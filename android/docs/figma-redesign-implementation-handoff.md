## 확정한 공통 결정

- 앱 일반 텍스트는 **Gowun Dodum Regular**, 문자로 표시하는 기호 아이콘은 **Pretendard**를 사용한답니다. 벡터 아이콘에는 글꼴 변경을 적용하지 않는답니다.
- 탐색 구조는 **홈, 피드, 발견, 내 서재의 4탭**이랍니다.
- 색상, 간격, 모서리, 글꼴 역할은 Figma의 `책췍 / Primitives`, `Semantic`, `Layout`, `Typography` 변수와 `책췍/` 스타일을 코드의 공통 테마와 컴포넌트에 연결한답니다. 각 화면에 동일한 값을 중복 선언하지 않는답니다.
- 일반 다이얼로그와 시트 버튼의 텍스트는 중앙 정렬한답니다. 공급업체 로그인 버튼에는 앱 공통 버튼 스타일을 강제로 적용하지 않는답니다.
- 가운데점 U+00B7을 UI 문구나 설명의 장식, 항목 구분자로 사용하지 않는답니다. 문맥에 맞는 문장, 괄호, 쉼표, 줄바꿈, 레이아웃 간격으로 구분한답니다. 기존 코드의 문구도 적용 화면 범위에서 확인한답니다.
- 프로젝트 스킬의 과거 3탭, 시스템 글꼴, 이전 시안 안내가 이 문서와 충돌하면 사용자가 지정한 최신 Figma와 이번 결정이 우선한답니다. 접근성, Dynamic Type, 입력과 화면 흐름 검증은 계속 필요한 것이랍니다.

## Google과 Apple 로그인 예외

- Google 버튼은 재디자인 이전 구현의 로고, 서체, 색상, 형태를 유지하라는 사용자 결정이랍니다. 일반 텍스트의 Gowun Dodum을 공급업체 버튼 내부에 적용하지 않는답니다.
- Google 예시 인스턴스는 `915:35`, 로그인 실패의 `915:54`이며, 예시 마스터는 `924:205`이랍니다.
- iOS의 기존 Google 구현은 `android/iosApp/Chaekchaek/ContentView.swift`의 `GoogleSignInControl`이랍니다. 실제 코드가 커스텀 래퍼라는 점과 공식 SDK 버튼이라는 주장은 구분해야 한답니다. 기존 구현 유지가 최신 공급업체 규정 준수 검증을 대신하지 않는답니다.
- Apple 예시 마스터는 `925:203`, iOS 샘플 내부 인스턴스는 `925:217`이랍니다. 공식 Apple 버튼 자산으로 만든 시안이며 앱에서는 기존 네이티브 Apple 로그인 컨트롤을 유지한답니다.
- `android/shared/src/commonMain/kotlin/com/chaekchaek/app/ui/common/AppleSignInButton.kt`의 expect와 플랫폼별 actual 구현을 확인한답니다. Figma의 이미지 자산을 네이티브 버튼 대신 단순 클릭 이미지로 구현하지 않는답니다.
- 플랫폼별 제공 여부와 기존 로그인 콜백, 로딩, 실패, 취소 동작을 유지한답니다.

## 시작 시 코드와 브랜치 확인

인계 시점의 주 작업 체크아웃은 `codex/font-comparison`, HEAD `9d16be00`이며 추적 파일의 미커밋 변경은 없었답니다. `origin/an-develop`은 `3d556e71`이며 프로젝트 메모리의 Figma 디자인 시스템 기준이 이 커밋에 기록되어 있답니다.

두 기준은 동일하지 않답니다. 현재 앱 변경과 글꼴 리소스, 디자인 검사기가 로컬 브랜치에 있고 원격 통합 브랜치와 차이가 있으므로, 새 세션에서 다시 fetch하고 로그와 diff를 확인한답니다. 글꼴 비교용 브랜치를 이름이나 현재 체크아웃이라는 이유만으로 전체 재디자인 구현에 재사용하지 않는답니다. 원격 기준에서 누락되는 변경에 의존한다면 사용자의 브랜치 규칙에 따라 분기 기준을 먼저 확정한답니다. 임의로 기존 커밋을 이동하거나 모든 차이를 통합하지 않는답니다.

현재 로컬 `ChaekchaekTheme.kt`에는 Gowun Dodum 리소스와 `ChaekIconFontFamily()`가 있지만 `ChaekchaekTheme`의 기본 후보는 **NanumGothic**이랍니다. 리소스 존재를 앱 기본 글꼴 적용 완료로 해석하지 않는답니다. 이 인계의 글꼴 결정을 실제 기본 테마와 사용자 표시 텍스트에 적용해야 한답니다.

문서만 바꾸는 작업은 프로젝트 규칙에 따라 `an-develop`에 직접 커밋과 push할 수 있답니다. 앱 코드 구현은 별도 작업이며 이슈, 브랜치, Draft PR 절차와 각각의 생성 승인 규칙을 확인한답니다. 이번 문서 요청은 이슈나 PR 생성 승인이 아니랍니다.

2. Figma의 주요 화면, 추가 시안, 변수와 컴포넌트를 읽고 현재 앱의 실제 진입점에 대응표를 만든답니다. 상태와 플랫폼별 적용 여부를 기록한답니다.
3. 글꼴과 토큰, 공통 입력과 버튼, 다이얼로그와 시트부터 연결하고 화면별 구현을 진행한답니다. 기존 인증, 저장, 삭제, 오류 처리와 API 계약을 유지한답니다.
4. 변경 범위에 맞는 빌드와 기존 동작 테스트를 실행한답니다. 별점 0.5점 선택, 필수 감상과 입력 범위, 취소 후 복귀처럼 실제 동작을 검증한답니다.
5. Android와 iOS에서 실제 진입점으로 화면을 열고 캡처한답니다. 390과 320 너비, 키보드, 긴 제목과 감상, 빈 상태, 실패 상태, 버튼 중앙 정렬, 별점 터치 영역을 확인한답니다.
6. iOS는 관련 검증 스킬을 통해 기본 Dynamic Type과 AX5를 확인하고 가능한 환경에서 접근성 감사를 실행한답니다. 실행하지 못한 플랫폼이나 상태는 미검증으로 남긴답니다.
7. 원본 노드, 구현 파일, 플랫폼, 뷰포트, 실행 상태, 캡처 위치를 결과에 기록하고 의미 단위로 커밋한답니다. Figma 제작이나 빌드 성공만으로 앱 적용 완료라고 보고하지 않는답니다.

로컬 브랜치의 디자인 검사기는 `android/visual-contracts/README.md`에서 절차를 확인한답니다. 이전 `chaekchaek.job.json`의 원본 ID와 참조 이미지가 이번 `822:*`, 추가 `913:*` 시안과 다를 수 있으므로 그대로 최신 검증이라고 주장하지 않는답니다. 최신 원본을 수집하고 이번 노드와 상태, 플랫폼, 캡처로 작업 계약을 갱신한답니다.

검사기가 있는 기준 브랜치에서는 `android` 디렉터리에서 다음 명령을 사용한답니다. 작업 JSON의 경로는 실제 준비한 최신 계약으로 지정한답니다.

```sh
./gradlew testDesignUiHarness testChaekchaekVisualAdapter
./gradlew verifyDesignUi -PdesignJob=<최신-작업-json>
```

pending과 blocked 항목을 일괄 통과시키거나 검토 목록을 삭제해서 완료 처리하지 않는답니다. 이 검사기의 통과는 검토 커버리지 근거이며 자동 픽셀 일치나 실제 사용자 흐름 성공을 보장하지 않는답니다.

## 이 세션의 확인 범위

- Figma MCP로 주요 화면 5개, 추가 화면 묶음과 디자인 시스템의 현재 노드와 스타일을 읽었답니다. 일반 스타일의 Gowun Dodum과 문자 아이콘의 Pretendard를 확인했답니다.
- 직전 디자인 수정에서 감상 작성, 수정, 320 시안은 프레임 내 잘림이 없었고, 별점 영역은 각 약 55.6 x 56px로 확인했답니다. 이는 Figma 배치 근거이며 앱 실행 근거가 아니랍니다.
- 가운데점 문구 정리는 승인된 결정이랍니다. 인계 시점 재조회에서는 추가 페이지에 가운데점을 포함한 텍스트 1개가 다시 확인되었으므로 최신 문구를 재확인하고 결정대로 적용한답니다.
- 앱 적용은 아직 별도 작업이랍니다. 새 세션에서 실행과 캡처로 확인해야 한답니다.

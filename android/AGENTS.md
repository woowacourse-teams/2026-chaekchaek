# 책췍 Android 작업 규칙

## 작업 범위

- 이 프로젝트의 코드, 문서, 설정, AI 작업 규칙과 스킬은 저장소의 `android/` 안에서만 작성하거나 수정한다. Android와 iOS KMP 앱 모두 이 범위에 속한다.
- 명령은 기본적으로 `android/`를 작업 디렉터리로 실행한다. 이 문서의 Markdown 링크도 `android/`를 기준으로 해석한다. 본문에 명시한 `android/...` 경로는 저장소 루트 기준이다.
- 유일한 공통 경로 예외는 Android 자동 검증을 위한 저장소 루트의 `.github/workflows/android-ci.yml`이다.
- `frontend/`, `backend/`, 루트 README, 공통 PR 템플릿, 루트 `.gitignore`와 다른 공통 설정은 이 작업 범위에 포함하지 않는다. 별도 사용자 지시 없이 변경하거나 커밋에 포함하지 않는다.
- main 반영용 브랜치는 최신 main에서 시작하고 Android 결과물만 가져온다. an-develop 전체를 병합해 frontend 변경이나 그 커밋 이력을 포함하지 않는다.
- 설치, 조회, 빌드, 테스트처럼 저장소 파일을 변경하지 않는 작업에는 새 브랜치를 만들지 않는다.
- Codex와 Claude Code는 이 문서를 함께 사용한다. `CLAUDE.md`는 이 문서를 가리키는 심볼릭 링크다.

## 문서 이동과 main 반영

- main 반영 범위, 원본 커밋, 이동된 자산과 제외 경로를 확인하거나 후속 통합을 준비할 때는 [main 반영 가이드](docs/main-integration.md)를 먼저 읽는다.
- 지속 보관할 문서를 이동하거나 갱신할 때는 `document-memory-routing` 스킬로 이 문서와 [문서 인덱스](docs/document-routing.md)의 읽기 조건과 상대 경로를 함께 수정한다.

## AI 작업 설정 예외

- `AGENTS.md`, `CLAUDE.md` 등 AI 에이전트 작업 설정 변경은 별도 GitHub 이슈, 작업 브랜치,
  PR 없이 `an-develop`에 직접 커밋하고 push할 수 있다.
- 이 예외는 `main` 브랜치 보호 규칙에는 적용하지 않는다.

## GitHub 작업 흐름

- 현재 프로젝트에서는 Notion 칸반 단계를 사용하지 않는다.
- 새 작업은 GitHub 이슈 생성, 작업 브랜치 생성, Draft PR 생성, 구현 및 검증 순서로 진행한다.
- GitHub 이슈에는 저장소에 이미 존재하는 범위 및 작업 유형 라벨을 적극적으로 적용한다.
- `/android` 스코프의 GitHub 이슈와 `an-develop` 대상 PR 제목은 반드시 `[AN] `으로 시작한다.
- 이슈와 PR 생성 승인용 제목 초안에 `[AN] `을 포함하고, 생성 직후 실제 제목에도 접두사가
  적용됐는지 GitHub CLI로 확인한다.
- GitHub 이슈 생성 승인을 요청하기 전에 이슈 제목, 본문, 적용할 라벨 초안을 먼저 작성해
  사용자에게 제시한다. 사용자의 초안 검토가 끝난 뒤에만 `슛` 승인을 요청한다.
- 사용자가 이슈 초안 수정을 요청하면 수정안을 다시 제시하며, 초안에 대한 확인이나 수정 요청을
  이슈 생성 승인으로 간주하지 않는다.
- Draft PR 생성 승인을 요청하기 전에 PR 제목과 본문 초안을 먼저 작성해 사용자에게 제시한다.
  사용자의 초안 검토가 끝난 뒤에만 PR 생성을 위한 별도의 `슛` 승인을 요청한다.
- 사용자가 PR 초안 수정을 요청하면 수정안을 다시 제시하며, 초안에 대한 확인이나 수정 요청을
  PR 생성 승인으로 간주하지 않는다.
- 이슈와 PR 생성 승인은 아래 승인 규칙을 따른다.
- GitHub 이슈 또는 PR 생성 전 제목과 본문 초안을 제시하고, 사용자가 독립된 메시지로 정확히 `슛`이라고 답한 뒤에만 생성한다. `슛` 한 번은 생성 한 건만 승인한다.
- main 반영용 커밋은 기존 main CI가 검사하는 `[AN] type(scope): 한글 요약` 형식을 사용한다. 공통 커밋 검사 workflow는 변경하지 않는다.

## 디자인 원본과 디자인 시스템

- 현재 UI 디자인 원본은 [책췍 Figma](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr)이며, 이번 작업에서 사용자가 지정한 최신 승인 화면을 우선한답니다.
- 공통 스타일과 컴포넌트는 [책췍 · 디자인 시스템](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=901-300)을 기준으로 사용한답니다.
- 일반 텍스트는 Gowun Dodum Regular, 문자로 표현한 아이콘은 Pretendard를 사용한답니다. 벡터 아이콘을 글꼴 변경 대상으로 취급하지 않으며, 공급업체 네이티브 로그인 컨트롤은 해당 공급업체 규격을 유지한답니다.
- 색상·간격·모서리·타이포그래피는 Figma의 책췍 / Primitives, Semantic, Layout, Typography 변수와 책췍/ 스타일을 재사용한답니다. 기존 컴포넌트의 인스턴스와 상태 변형을 먼저 사용하고, 반복되는 새 요소는 공통 컴포넌트로 추가한답니다.
- 탐색 구조는 홈·피드·발견·내 서재 4탭이며, 최신 Figma 기준이 과거 가이드의 3탭·시스템 글꼴·주황 활성 표시점 지침보다 우선한답니다.
- [추가 화면 재디자인](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=913-2)은 기존 미반영 화면과 팝업의 후속 시안이랍니다. Figma 시안 제작을 앱 구현 완료로 간주하지 않으며, 실제 반영 시 원본 노드·상태·플랫폼·뷰포트를 명시하고 캡처로 검증한답니다.
- Pencil과 designs.pen은 과거 이력이며 현재 원본이나 구현 게이트로 사용하지 않는답니다. 기존 로컬 핸드오프와 충돌하면 사용자가 지정한 최신 승인 산출물을 우선한답니다.
- 외부 디자인 도구 반영은 사용자가 지정한 순서와 승인 범위에 맞춰 수행한답니다.

### 디자인 적용 전 Figma 확인과 공통 컴포넌트 등록

- UI 디자인을 생성하거나 코드에 적용하기 전에 `android/.agents/skills/chaekchaek-design-system/SKILL.md`를 읽고 Figma MCP로 대상 화면과 디자인 시스템을 실제 조회한다. 과거 캡처, 로컬 HTML, 코드 또는 이전 세션 기록만으로 확인을 대신하지 않는다.
- 대상 화면이나 필요한 상태가 Figma에 없으면 먼저 Figma에 생성한다. 결과를 바꿀 미확정 디자인은 사용자에게 확인하고, 기존 구현의 역반영 요청은 지정된 구현과 캡처를 기준으로 삼는다.
- 공통 요소는 디자인 시스템의 메인 컴포넌트 또는 컴포넌트 세트와 [공통 컨트롤 레퍼런스](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=905-153)를 각각 확인한다. 검색 결과가 비어 있어도 캔버스의 로컬 컴포넌트를 조회한다. 화면에 같은 모양의 프레임이 있다는 사실은 공통 컴포넌트 등록 증거가 아니다.
- 메인 컴포넌트가 없으면 기존 변수와 스타일로 생성하고, 레퍼런스에 없으면 해당 메인 컴포넌트에 연결된 인스턴스로 상태별 예시를 추가한다. 이미 있으면 재사용한다. 정적 이미지나 분리된 복제 프레임으로 등록을 대신하지 않는다.
- 코드 적용 전 대상 화면, 공통 컴포넌트, 레퍼런스의 노드 링크와 필요한 상태를 확인하고 캡처로 검증한다. 생성 성공만으로 끝내지 말고 인스턴스 연결, 상태, 글꼴, 잘림과 겹침을 확인한다.
- Figma 접근 또는 등록에 실패하면 해당 UI의 코드 적용을 진행하거나 디자인 반영 완료로 보고하지 않는다. 차단 원인과 미완료 항목을 알린다. 파일 내 등록과 팀 라이브러리 게시를 구분하고, 실제 게시 확인 없이 게시 완료라고 표현하지 않는다.
- 이 절차는 Codex와 Claude Code 모두에 적용한다. 과거 Pencil 절차나 HTML 시안 절차보다 우선하며, 자동 훅을 다시 설치하는 규칙은 아니다.

## 문서 규칙

- 앱 구조, 도메인, API, 인증 권한, 상태 복원을 다룰 때는 [설계와 동작 문서 라우팅](docs/document-routing.md#architecture)을 먼저 확인하고 해당 작업의 원문을 읽는다.
- 화면 디자인, UI 회귀 검증은 [디자인과 검증](docs/document-routing.md#design), 빌드, 서버 환경, CI, 스토어 심사는 [개발과 배포](docs/document-routing.md#delivery)의 해당 문서를 먼저 읽는다.
- 이벤트 계측, 사용자 관찰, 웹 읽기 실험, 작가 협업, 과제 제출은 [실험과 운영](docs/document-routing.md#research)의 해당 문서를 먼저 읽는다. 과거 핸드오프와 초안은 인덱스에 명시한 확인 범위로만 사용한다.

- 첫 책 온보딩, 로그인 후 서재 저장, 공급업체 로그인 버튼의 디자인이나 구현을 변경할 때는 [첫 책 선택 온보딩](docs/first-library-onboarding.md)을 먼저 읽는다. 로그인 버튼은 문서의 공급업체 제약과 검증 상태를 확인한다.

- Google 로그인 조사, 패키지명/빌드 변형/OAuth 클라이언트/Play 앱 서명 키 변경 및
  Android 로그인 배포 검증은 [Google 로그인 운영 가이드](docs/android-google-login.md)를 먼저 읽는다.
  실제 Play 서명 지문 등록과 배포본 로그인 완료를 확인하기 전에는 해결 완료로 판단하지 않는다.

- 레벨4 과제 제출에 필요한 LMS 안내와 제출 양식은
  [레벨4 과제 제출 문서](docs/level4-submission/README.md)를 먼저 참고한다.
- Android 개발자 도구와 상태 보존 요구사항을 제출하거나 완료 근거를 갱신할 때는
  [Android 개발자 도구와 상태 보존 제출 문서](docs/level4-submission/android-developer-tools-state-preservation.md)를 먼저 읽는다.

- 책등 이미지, YES24 SIDE 이미지, 피드·서재의 표지 대체 표현을 다룰 때는
  [책등 이미지 활용 메모](docs/book-spine-images.md)를 먼저 읽는다. 과거 프론트 테스트는
  YES24 상품번호로 `/goods/{상품번호}/SIDE/XL` URL을 조합했다. 백엔드 API 구현이나
  모든 책의 이미지 제공이 확인된 것으로 해석하지 않는다.

- 오래 유지할 프로젝트 문서는 `android/docs`에 Markdown 파일로 둔다.
- 각 디렉터리의 README는 해당 문서를 찾는 짧은 라우팅·시작 안내만 둔다. 상세 운영 절차나
  설계 설명을 README에 누적하지 않는다.
- 새 문서에는 목적을 드러내는 kebab-case 파일명을 쓰고, 관련 README에서 링크한다.
- Markdown 문서만 변경하는 독립 작업은 GitHub 이슈, 작업 브랜치, PR 없이 `an-develop`에
  직접 커밋하고 push한다.
- 기능이나 코드 변경에 수반되는 문서 변경은 해당 작업 브랜치와 PR에 함께 포함한다.

## an-develop 브랜치 운영

- `an-develop`은 현재 사용자 한 명이 관리하는 통합 브랜치이므로 PR 없이 직접 push해도 된다.
- `origin/an-develop`을 원격의 최신 기준으로 유지한다.
- `an-develop-local`은 로컬 작업·검증 전용이며 원격 브랜치로 push하지 않는다. 작업 완료 후
  `an-develop-local`의 HEAD를 `origin/an-develop`에 fast-forward로 반영한다.

## main 브랜치 보호 (필수)

- main에 직접 push하거나 merge하지 않는다. 예외 없음.
- 모든 변경은 별도 브랜치에서 작업한 뒤 PR(Pull Request)을 통해서만 main에 반영한다.
- 작업 중인 도구가 Codex든 Claude Code든 이 규칙은 동일하게 지킨다.

## 앱 전반 리플 금지 (2026-10-12)

- 책췍 앱의 모든 화면과 공통 컴포넌트에서 터치 리플을 사용하지 않는다. Android와 iOS가
  공유하는 Compose UI에도 동일하게 적용한다. 새 UI와 기존 UI 수정 모두 이 규칙을 따른다.
- 명시적인 `ripple`/`rememberRipple` 추가뿐 아니라 `clickable`, `selectable`, `toggleable`과
  Material 버튼, 클릭 가능한 `Surface`, 메뉴 항목 등이 기본으로 제공하는 리플도 허용하지 않는다.
- 공통 테마와 컨트롤에서 리플 차단을 보장하고, 화면별 재정의나 새 컴포넌트가 이를 우회하지
  않는지 확인한다. 단순히 코드에서 `ripple` 문자열이 검색되지 않는 것으로 검증을 대신하지 않는다.
- 리플 제거 시 클릭과 길게 누르기, 선택 상태, 비활성 상태, 접근성 역할과 터치 영역은 유지한다.
  다른 터치 애니메이션을 임의로 추가하지 않는다.
- 실제 터치 검증에는 화면, 버튼, 탭, 카드, 필터, 드롭다운, 다이얼로그와 바텀시트를 포함한다.
  지침 기록이나 정적 조사만으로 기존 앱의 리플 제거가 완료됐다고 보고하지 않는다.

## 모든 텍스트 필드의 입력 크기 제한 (필수)

- Android와 iOS가 공유하는 모든 텍스트 필드에 적용한다. 검색, 닉네임, 감상, 인용 문구,
  목차·챕터, 답글, 쪽수, 도서 등록 필드를 포함하며 새 필드에도 예외를 두지 않는다.
- 필드마다 최대 길이와 길이 단위(code point 또는 UTF-16), 허용 문자 정책을 명시한다.
  기존 서버 검증과 도메인 제약을 유지하며, 기준이 불명확하면 구현 전에 확인한다.
- 직접 입력과 붙여넣기는 편집 단계의 `InputTransformation`에서 제한한다. 서버·기기 저장소의
  초기값, 코드로 대입하는 값, 저장 상태 복원값에도 같은 공통 정책을 적용한다.
  `onValueChange`나 제출 시점의 검사만으로 입력 보호를 대신하지 않는다.
- 제한한 값만 화면 상태와 저장 상태에 넣는다. `rememberSaveable`의 초기화·저장·복원과
  `SavedStateHandle`의 읽기·쓰기를 함께 확인하고, 이전 버전의 긴 초안도 복원 시 제한한다.
  대량 입력을 자르기 위해 초과 부분 전체를 불필요하게 복사하지 않는다.
- UTF-16 surrogate pair를 분리하거나 짝이 없는 surrogate를 남기지 않는다. 중간 삽입과
  선택 영역 교체에서는 허용량만 받아들이고 기존 뒤쪽 문장을 보존한다. 커서와 선택 영역도
  유효한 문자 경계 안으로 보정한다.
- 한글 IME 조합, 커서 이동, 선택·삭제, 길게 누르기·붙여넣기, 키보드 제출과 접근성 동작을
  유지한다. 화면별 임의 자르기 대신 입력·초기값·저장·복원이 같은 제한 정책을 재사용한다.
- 제한 변경 시 경계값, 대량 입력·붙여넣기, 한글·이모지·잘못된 surrogate, 중간 삽입·선택
  교체, 초과 초기값·이전 초안 복원과 재저장을 회귀 테스트로 검증한다. Android와 iOS에서
  실제 편집·붙여넣기·복원을 확인하고, 빌드·단위 테스트와 기기 검증 결과를 구분한다.
  실행하지 못한 플랫폼이나 경로를 검증 완료로 보고하지 않는다.

"제 컴퓨터에서는 빌드되는데요" 문제와 keystore가 한 사람 로컬에만 있어 그 사람이 빠지면
배포가 멈추는 문제를 막기 위한 요구 사항. 반드시 지킬 것.

## 도착 조건 (완료 기준)
- 팀원 누구나 문서를 따라 릴리스 서명이 붙은 빌드 결과물을 만들 수 있다.
- minSdk / targetSdk 를 몇으로 정했는지와 그 이유가 문서화되어 있다.
- keystore와 비밀번호가 특정 팀원 1인의 로컬에만 있지 않고, 2인 이상이 접근 가능한 곳에
  보관되어 있다.

## 학습 조건 (팀원이 설명할 수 있어야 함)
- Gradle 빌드 구성(빌드 타입, 서명 설정, 의존성 관리)을 직접 작성하고 각 설정이 무엇을
  하는지 설명할 수 있다.
- minSdk 결정이 지원 기기 범위와 사용 가능한 API를 어떻게 바꾸는지 설명할 수 있고,
  targetSdk 가 스토어 정책과 연결된다는 것을 안다.
- 업로드 키와 앱 서명 키의 차이를 이해하고, 키를 잃었을 때 무엇이 불가능해지는지
설명할 수 있다.

## Android 앱 버전 및 릴리스 커밋 (2026-08-21)

- 앱 버전의 단일 출처는 `app/build.gradle.kts`의 `defaultConfig`에 있는 `versionCode`와
  `versionName`이다. 다른 파일에 같은 값을 중복 선언하지 않는다.
- Play에 빌드를 올릴 때마다 `versionCode`를 Play Console에서 사용한 최댓값보다 크게 올린다.
  기본 증가 폭은 1이다.
- `versionName`은 SemVer(`MAJOR.MINOR.PATCH`)를 따른다. 변경 성격에 따라 모델이 증가 단위를
  판단한다. 호환되지 않는 변경은 major, 호환되는 기능 추가는 minor, 호환되는 버그 수정은
  patch다. 기존 심사 버전 `1.0`은 유지하고 다음 버전부터 세 자리 형식을 적용한다.
- 버전과 배포 상태, 변경 내역, 복구 기준은
  [`docs/android-release-management.md`](docs/android-release-management.md)에 함께 기록한다.

릴리스 절차는 `android` 디렉터리에서 아래 순서로 진행한다. 각 Android 명령을 실행하기 전에
명령의 목적을 한 줄로 먼저 설명한다.

1. `app/build.gradle.kts`의 두 버전과 릴리스 관리 문서를 갱신한다.
2. `./gradlew :app:assembleDebug`로 기본 컴파일과 패키징을 확인한다.
3. `./gradlew :app:verifyReleaseSigning`으로 릴리스 서명 설정을 확인한다.
4. `./gradlew :app:bundleRelease`로 서명된 AAB를 만든다.
5. `jarsigner -verify app/build/outputs/bundle/release/app-release.aab`로 서명을 검증한다.
6. AAB의 SHA-256을 릴리스 관리 문서에 기록하고 Play Console의 대상 트랙에 업로드한다.
7. 배포 후 release 커밋을 남긴다. 포맷과 변경 목록 추출은 `release-commit` 스킬을 따른다.

release 커밋 제목은 항상 `chore(release): vX.Y.Z 배포`로 쓴다. 본문 첫 줄에는 아래 형식으로
배포 대상, `versionName` 증감과 SemVer 증가 단위, `versionCode` 증감을 적는다.

```text
대상: Google Play <트랙> / A.B.C -> X.Y.Z (major|minor|patch), versionCode M -> N
```

본문 변경 목록은 직전 release 커밋 이후의 `git log`에서 추출하고 임의로 누락하지 않는다. 본문
맨 끝에는 실제 배포 트랙과 AAB 해시를 아래 형식으로 남긴다.

```text
Play track: <internal|closed|open|production>
AAB SHA-256: <hash>
```

## Google Play 게시와 사용자 관찰 (2026-08-28)

- 프로덕션 `1.0 (2)`는 심사를 통과해 관리형 게시 대기 상태다.
- 에이전트는 프로덕션 게시 버튼을 누르지 않는다. 게시 여부는 사용자가 직접 결정한다.
- Play Console의 타겟 연령은 16-17세와 만 18세 이상이며 임의로 변경하지 않는다.
- 사용자 관찰 계획과 결과는
  [`docs/android-production-review-user-observation.md`](docs/android-production-review-user-observation.md)에
  기록한다.
- 미성년자 관찰은 보호자 동의를 받은 뒤 진행하고, 개인 식별 정보는 저장소에 기록하지 않는다.

## 화면 이동과 뒤로가기 안전 규칙 (필수)

- Navigation3의 화면 목록은 항상 루트 화면을 포함해야 한다. 뒤로가기나 앱 종료를 위해
  마지막 항목을 제거하거나 목록을 비우지 않는다. 앱 종료는 플랫폼 종료 처리로 분리한다.
- 화면 목록 변경은 공통 이동 처리로 캡슐화한다. 화면별 콜백에서 직접 추가·삭제하지 않으며,
  공통 처리에서 루트 보존과 중복 진입·복귀 방지를 보장한다.
- 뒤로가기 요청은 요청한 화면 진입이 현재 유효한 최상위 진입일 때만 처리한다. 이미 닫힌
  화면의 연속 입력이나 재진입 전의 지연 콜백이 다른 화면을 닫지 않도록 한다.
- 시스템 버튼·제스처, 화면 아이콘·버튼, 로그아웃·탈퇴·인증 완료 등 비동기 이동 경로에
  같은 안전 규칙을 적용한다. 시간 기반 연타 제한만으로 상태 검증을 대신하지 않는다.
- 팝업·바텀시트가 처리한 뒤로가기 이벤트가 아래 화면에도 중복 적용되지 않도록 한다.
  기존 입력 폐기 확인과 인증 취소 정책을 유지하고, 닫힌 UI의 응답이 새 UI를 변경하지 않게 한다.
- 화면 이동을 변경할 때 루트 반복 복귀, 중복 진입·닫기, 화면 재진입 후 이전 콜백 도착,
  비동기 완료와 뒤로가기의 순서 교차를 회귀 테스트로 검증한다.
- 실제 앱에서는 영향받는 화면과 팝업의 시스템 뒤로가기·아이콘 혼합 연타, 제스처 취소,
  정상 종료·재실행을 확인한다. 빌드·단위 테스트만 통과한 상태를 실기기 검증으로 보고하지 않는다.

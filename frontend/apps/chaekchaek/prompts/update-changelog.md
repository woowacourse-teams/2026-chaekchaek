# 프론트엔드 릴리즈 CHANGELOG 작성

## 목적

`fe-develop`에서 `fe`로 병합하는 릴리즈 PR의 변경 사항을 확인하고, 병합 전에 프론트엔드 `CHANGELOG.md`를 작성한다.
각 항목은 기존 기록처럼 변경 대상과 핵심 변화가 바로 드러나는 짧은 구절로 작성한다.

## 입력값

- 원격 저장소: 기본 `origin`. 실제 설정이 다르면 해당 이름을 사용한다.
- base 브랜치: 기본 `fe`
- head 브랜치: 기본 `fe-develop`
- 릴리즈 버전: 사용자가 제공한 값을 사용한다.
- 릴리즈 PR 번호 또는 URL: 제공되면 해당 PR의 base/head와 변경 내용을 확인한다.
- 사용자가 다른 비교 범위를 명시하면 그 범위를 우선한다.

버전이 없으면 변경 사항 조사와 채팅 초안까지 작성하고, 파일 반영에 필요한 버전이 미정임을 알린다.
버전을 추측하거나 `X.X.X`, `Unreleased`, 배포 날짜를 임의로 기록하지 않는다.

## 조사 절차

1. 저장소의 작업 지침과 기존 프론트엔드 `CHANGELOG.md`를 읽는다.
   최근 버전의 문체, 상세 수준, 항목 구성과 버전 정렬 순서를 확인한다.
   이 프로젝트의 1.3.0·1.4.0처럼 분류 아래에 변경 사항을 나열하는 형태를 기본으로 삼는다.

2. `git fetch origin`으로 원격 추적 브랜치를 갱신한다.
   일부 브랜치만 fetch하도록 설정되어 있으면 필요한 refspec으로 대상 브랜치를 가져온다.
   갱신한 `origin/fe`와 `origin/fe-develop`를 비교하고, 기준으로 사용한 커밋을 기록한다.
   비교만을 위해 두 로컬 브랜치를 각각 checkout하거나 pull할 필요는 없다.
   갱신에 실패하면 확인 가능한 범위까지 조사하고 최신성을 확인하지 못했음을 알린다.

3. 이번 릴리즈의 변경 파일, 커밋, 관련 기능·수정 PR을 조사한다.
   PR 번호, URL, 본문은 사용 가능한 GitHub 도구 또는 GitHub CLI로 확인한다.
   날짜나 최근 커밋 개수로 범위를 정하거나, 원격에 없는 로컬 변경을 임의로 포함하지 않는다.

4. PR 제목과 커밋 메시지를 단서로 사용하고, 실제 코드 변경으로 의미와 적용 여부를 확인한다.
   커밋 목록만으로 포함 여부를 확정하지 말고, 기존 릴리즈 기록과 최종 변경을 대조한다.
   이미 릴리즈한 변경, 되돌려져 남지 않은 변경, 단순 merge 기록, CHANGELOG 작성 자체는 제외한다.
   `fe`에만 있는 수정이 `fe-develop`에 없다는 이유로 기능이 제거되었다고 단정하지 않는다.

5. 확인이 불충분한 변경은 확정 항목에 섞지 말고 최종 보고에 따로 적는다.

## 분류와 출력 형식

- 사용할 수 있는 분류와 순서는 `Added → Changed → Fixed → Improved`다.
- **실제 항목이 있는 분류만 출력한다. 빈 분류는 제목까지 생략한다.**
- `없음`, `해당 없음`, 빈 목록 등으로 분류를 채우지 않는다.
- 이번 버전에 이미 빈 분류 제목이 있다면 제거한다.
- 기록할 변경이 전혀 없으면 빈 버전 섹션을 만들지 말고 그 사실을 알린다.

| 분류 | 기준 |
| --- | --- |
| Added | 새로 제공하는 기능 |
| Changed | 기존 기능의 동작·정책·API 계약 변경 또는 기능 제거 |
| Fixed | 의도한 동작과 다르게 작동하던 오류 수정 |
| Improved | 성능·접근성·사용성 또는 개발·배포 환경 개선 |

변경의 주된 목적에 따라 한 곳에만 분류한다.
과거 기록의 문체와 상세 수준은 참고하되, 분류 오류·오탈자·깨진 링크는 새 항목에 반복하지 않는다.

파일 제목은 `# CHANGELOG.md`, 버전 제목은 `## X.X.X` 형식을 사용한다.
파일 제목은 맨 위에 한 번만 두고, 버전 제목에 날짜나 대괄호를 붙이지 않는다.

아래는 Changed에만 항목이 있는 경우의 형식 예시다. 나머지 분류의 제목은 작성하지 않는다.
`X.X.X`, `PR번호`, `PR_URL`은 실제 확인한 값으로 바꾼다.

```markdown
# CHANGELOG.md

## X.X.X

### Changed

- 책 검색 실행 조건을 Enter 입력·검색 버튼 클릭으로 변경 [#PR번호](PR_URL)
```

## 간결하게 작성하는 기준

- 각 항목은 **변경 대상 + 핵심 변화**로 작성한다.
  예: `답글 수정 및 삭제 기능 추가`, `PMF 설문 기능 추가`.

- 기본은 PR 링크를 제외하고 한 줄에 읽히는 짧은 구절이다.
  `추가`, `변경`, `수정`, `개선`, `제거`, `표시`, `숨김` 등으로 마무리한다.

- `~할 수 있도록 처리`, `~인 경우 ~하도록 변경` 같은 긴 서술은 짧게 바꾼다.
  조사·연결어를 기계적으로 없애기보다 자연스럽게 이해되는 표현을 우선한다.

- 변경의 대상·동작·핵심 조건을 남긴다.
  로그인/비로그인 여부나 적용 화면처럼 의미를 바꾸는 조건은 필요한 만큼 유지한다.

- 개발 배경, 구현 순서, 내부 상태, 함수명·파일명·API 필드명은 변경을 이해하는 데 필요할 때만 적는다.

- PR 본문의 모든 설명을 옮기지 않는다. 세부 동작을 길게 이어 붙이지 말고 대표적인 변화를 요약한다.

- `기능 개선`, `로직 수정`, `UI 변경`처럼 무엇이 달라졌는지 알 수 없는 표현으로 줄이지 않는다.

- 짧게 쓰기 위해 의미를 확대하지 않는다.
  예를 들어 `닫기·취소 버튼 숨김`을 `닫기 차단`이나 `닉네임 설정 필수화`로 바꾸지 않는다.

- 성능 수치나 개선 효과는 확인한 근거가 있을 때만 적는다.

## 항목을 묶고 나누는 기준

- 하나의 기능을 구현·보완한 여러 커밋이나 PR은 하나의 항목으로 묶는다.

- 여러 화면에 동일한 변경이 적용되었다면 화면 이름을 함께 적고 설명은 한 번만 쓴다.

- 하나의 PR에 독립적인 변경이 있으면 항목을 나눌 수 있다.

- 한 기능에 중요한 하위 변경이 여러 개라 한 줄로 이해하기 어려울 때만 하위 목록을 사용한다.
  예: `감상 작성 기능 개편` 아래에 `쪽수·챕터 입력 제거`, `작성 화면에 별점 설정 추가`를 나열한다.

- 짧은 항목 하나를 위해 `####` 소제목이나 하위 목록을 만들지 않는다.
  소제목은 항목이 많아 기능별 구분이 필요한 경우에만 사용한다.

- 동작 변화가 없는 사소한 정리와 오탈자 수정은 기존 기록 기준에 따라 필요할 때만 포함한다.

## PR 연결 기준

- 변경 설명과 같은 줄 끝에 원래 기능·수정 PR을 `[#번호](URL)` 형식으로 연결한다.
- 관련 PR이 여러 개면 쉼표와 공백(`, `)으로 구분한다. 같은 항목에 같은 PR을 중복 연결하지 않는다.
- 릴리즈 PR 번호를 모든 항목의 근거로 일괄 사용하지 않는다.
- 실제 확인한 PR 번호와 URL만 사용하고, 번호와 링크 대상이 일치하는지 확인한다.
- 변경 내용은 확인했지만 관련 PR을 확인하지 못했다면 링크 없이 작성하고 최종 보고에 알린다.
- 예시의 번호나 과거 기록의 잘못된 URL을 그대로 복사하지 않는다.

## 파일 반영

- 기존 프론트엔드 CHANGELOG의 경로, 현재 작업 브랜치, 미커밋 변경을 확인한다.

- 최신 head 내용을 반영한 작업 브랜치에서 편집한다.
  현재 작업과 충돌하면 별도 작업 브랜치나 worktree를 사용하고 작업 위치를 알린다.
  기존 작업을 덮어쓰는 reset이나 강제 checkout은 수행하지 않는다.

- 기존 버전 정렬 순서를 유지하고, 이번 릴리즈 섹션만 추가하거나 보완한다.
- 같은 버전의 이번 릴리즈 초안이 있으면 갱신한다. 버전 제목이나 항목을 중복 추가하지 않는다.
- 이번 버전의 빈 분류 제목과 중복 항목을 제거하고, 긴 문장은 위 기준으로 다듬는다.
- 이전에 확정된 릴리즈 기록과 관련 없는 작성 내용은 보존한다.
- 기본 작업 범위는 CHANGELOG 파일 수정까지다.
  버전 파일 수정, commit, push, PR 생성, merge, tag, 배포는 사용자가 요청한 경우에만 수행한다.

## 최종 점검과 보고

이번 버전에 다음이 충족되는지 점검한다.

- 빈 분류 제목이나 빈 하위 소제목이 없는가?
- 각 항목에서 변경 대상과 핵심 변화가 바로 드러나는가?
- 의미를 유지하면서 더 줄일 수 있는 설명·반복·구현 세부사항이 남아 있지 않은가?
- 짧게 줄이는 과정에서 중요한 조건을 빠뜨리거나 의미를 확대하지 않았는가?
- 분류·항목·PR 링크가 중복되지 않았고, 링크 문법이 올바른가?
- 실제 변경과 내용이 일치하고, 기존 릴리즈 기록이 보존되었는가?

완료 후 수정한 파일과 버전, 비교 기준 커밋, 확인하지 못한 사항만 간단히 보고한다.

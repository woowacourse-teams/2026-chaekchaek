# 백엔드 개발 지침

이 문서는 백엔드의 개발 규칙과 작업 절차를 정의한다. 문서에 등장하는 프로젝트 내부 경로는 별도 언급이 없으면 `backend/`를 기준으로 한다.

기존 로컬 `AGENTS.md`의 우선 규칙과 개발 가이드를 함께 관리한다. **0절의 우선 적용 규칙은 1~10절의 일반 규칙보다 우선한다.** 허용된 예외를 일반 규칙 위반으로 판단하지 않는다.

## 0. 우선 적용 규칙

### 브랜치 이름

- `codex/` 접두사는 사용하지 않는다.
- 사용자의 기존 방식처럼 `feature/`, `fix/`, `refactor/`, `style/`, `chore/` 등 작업 성격에 맞는 접두사와 kebab-case 이름을 사용한다. 예: `chore/http-latency-histogram`.
- 에이전트가 만드는 브랜치에도 같은 규칙을 적용한다.

### 이슈와 PR의 내용 분리

아래는 사용자가 지정한 이슈 작성 기준이며, `development-guide.md`의 일반적인 이슈 구성 지침보다 우선 적용한다.

- 이슈 제목은 해결 방법이 아니라 사용자가 겪는 문제를 표현한다. 본문은 **문제 제기**와 **현행 분석**을 중심으로 작성하고, 재현 조건, 현재 동작, 영향, 확인된 원인과 근거를 담는다.
- 사용자가 제공한 노션 등 참고 자료에 문제 상황과 해결 방법 선택이 함께 있어도, 에이전트가 이슈에 필요한 문제 제기와 현행 분석만 추려 작성한다. 해결 결정, 구현 지시, 구현을 강제하는 체크리스트, 후보 비교는 자동으로 이슈에 옮기지 않는다. 사용자가 이슈에 특정 해결 방법을 명시하라고 직접 요청한 경우에는 그 요청을 따른다.
- 구현자는 해결 방법을 자율적으로 판단하고, 실제 구현 내용, 선택 이유, 검토한 후보와 장단점, 검증 결과를 PR에서 설명한다. 참고 자료에 있던 선택 근거는 원문 링크로 보존하고, 관련 구현을 수행할 때 PR에 반영한다.
- PR에는 최종 선택한 후보와 결정 근거, 다른 후보를 검토한 이점과 채택하지 않거나 보류한 이유, 아직 남아 있는 구현 후보와 검토 사항을 기록한다. 채택하지 않은 대안은 코드에서 확인할 수 없으므로 고려했던 목적과 장단점을 본문에 남긴다. 실제 구현, 검증한 내용과 미구현, 미검증, 후속 검토 사항을 구분하고, 노션에 결정이 있더라도 최종 구현과 달라졌다면 실제 선택과 변경 이유를 설명한다.
- 노션의 예시 사진, 현재 코드, 요청, 응답 예시 등 문제와 분석의 근거는 단순 요약이나 원문 링크만으로 대체하지 않고 가능한 한 그대로 이슈에 포함한다. 긴 코드, 응답 블록은 `<details>`로 접을 수 있게 하며, 해결 후보의 코드나 가상 결과를 현행 동작의 증거로 옮기지 않는다.
- 사진은 가능하면 GitHub 첨부로 옮겨 노션의 인증, 임시 이미지 주소에 의존하지 않게 하고, 실제 표시를 확인한다. 원본을 가져오거나 첨부할 수 없으면 그 한계를 알리고 원문 링크를 남긴다. 관찰한 사실과 추정은 구분하고, 특정 검색어의 비교 결과를 모든 검색 결과에 대한 보장으로 확대하지 않는다.

- 이슈, PR 본문에 `Generated by [Claude Code](https://claude.ai/code)` 같은 생성 도구 표시를 남기지 않는다. 도구가 자동으로 덧붙였다면 생성 후 본문에서 제거하고, 제거할 수 없으면 사용자에게 알린다.

### 이슈, 커밋, PR의 작업 단위

- 이슈는 문제와 진행 상황을 추적하는 단위, 커밋은 목적별로 검토, 검증, 되돌릴 수 있는 변경 단위, PR은 리뷰어가 하나의 완결된 동작을 판단하는 단위로 구분한다. 세 단위의 분리 기준을 각각 판단한다.
- 하위 이슈를 나눴다는 이유로 PR도 같은 개수로 나누지 않는다. 여러 하위 이슈를 하나의 PR에서 해결할 수 있다.
- 여러 변경이 같은 정책을 공유하고, 함께 적용해야 동작의 일관성이 완성되거나 여러 PR을 함께 읽어야 전체 동작을 판단할 수 있다면 하나의 PR로 묶는 구성을 우선 검토한다. 변경량과 PR 개수뿐 아니라 리뷰어가 전체 맥락을 이해하는 비용도 고려한다.
- 하나의 PR 안에서도 `development-guide.md`의 목적별 커밋 분리 규칙을 유지한다. 같은 상위 목표라는 이유만으로 독립적으로 검토, 검증, 되돌릴 수 있는 변경을 한 커밋에 합치지 않는다.
- 각 변경이 따로 병합돼도 의미 있는 개선을 완성하거나, 배포 시점과 호환성 조건이 다르거나, 공통 기반을 먼저 병합할 필요가 있으면 별도 PR로 나눌 수 있다. 같은 상위 목표에 속한다는 이유만으로 모든 변경을 한 PR에 묶지 않는다.
- 의존하는 PR을 차례로 쌓는 스택 PR은 각 PR이 병합 후 보장하는 동작과 선행 PR 의존성을 명확히 설명할 수 있을 때 사용한다. 분리로 얻는 이점과 반복 리뷰, 브랜치 재배치, 중간 상태의 불일치 비용을 함께 판단한다.
- 예를 들어 삭제 감상의 원문 노출, 목록과 페이지, 도서별 집계 문제는 하위 이슈로 추적하면서 조회 정책 전체를 한 PR에서 검토하고 목적별 커밋으로 나눌 수 있다. 클라이언트 배포와 맞춰야 하는 응답 필드 제거는 별도 PR로 분리할 수 있다.

### 글쓰기 표현

- 답변, 문서, 이슈, PR에서 항목을 나열할 때 가운데점 대신 쉼표(`,`)를 쓴다. 예: `보안 설정, REST Docs`.
- HTTP Method는 `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`처럼 인라인 코드로 표기한다. 본문, 목록, 표에서도 동일하게 적용한다.
- HTTP 상태 코드의 숫자(`200`, `401`, `403`, `404`)와 오류 식별자(`UNAUTHORIZED`, `FORBIDDEN`)도 인라인 코드로 표기한다. 본문, 목록, 표에서도 동일하게 적용한다.

- DB의 unique 제약은 `unique 제약`으로 표현한다. `유일 제약`이라는 번역은 사용하지 않는다.

### PR 본문 간결성

아래는 사용자가 지정한 PR 작성 기준이며, `development-guide.md`의 PR 구성, 검증 결과 기재 지침보다 우선 적용한다.

- 작업 내용은 새로 추가하거나 책임이 달라진 모델, 테이블, 주요 구성요소가 무엇을 맡는지와 왜 필요한지를 중심으로 설명한다. 예를 들어 `library_book`은 책장에 담긴 도서와 순서를 관리하고, 독서 정보는 `library_item`에서 공유해 여러 책장에 같은 도서를 담아도 중복되지 않게 한다고 설명한다.
- 파일별 수정 내역, 문구 정리 같은 부수 변경을 나열하기보다 리뷰어가 구조와 동작을 이해하는 데 필요한 내용을 우선한다. 모델 간 관계는 표로, 복잡한 구조나 흐름은 Mermaid 다이어그램이나 그림으로 보완할 수 있다. 본문과 그림에서 같은 설명을 길게 반복하지 않는다.
- PR 본문에 커밋 목록을 작성할 때는 `- [커밋 제목](커밋 URL)` 형식으로 제목에 해당 커밋의 링크를 연결한다. 해시는 본문에 별도로 나열하지 않고, 하위 설명에는 핵심 변경만 간결하게 적는다.
- 참고 사항에 로컬 검증 명령, 테스트 개수, `통과` 선언만 나열하지 않는다. GitHub Checks에서 확인할 수 있는 CI 상태도 본문에 반복하지 않는다. 테스트 코드나 CI로 확인할 수 없는 검증이 리뷰에 필요하면 재현 조건, 관찰 결과와 확인 가능한 근거를 짧게 제시한다.
- 테스트 코드와 diff에서 확인할 수 있는 테스트 목록, 성공과 실패 시나리오, 검증 범위를 PR 본문에 별도 절로 반복하지 않는다. 테스트 방식의 선택 이유, 수동 검증, 외부 환경의 제약이나 중요한 미검증 사항이 있을 때만 짧게 설명한다.
- 참고 사항에는 실제 영향, 제약, 미검증 범위와 남은 검토 사항만 간결하게 적는다. 적을 내용이 없으면 해당 절을 생략한다.
- PR 작성 전에 최종 diff와 관련 코드를 로컬에서 검토해 미사용 import, 생성자 파라미터, 테스트 헬퍼 등 정리 누락을 확인한다. 사소한 정리 사항은 PR의 잔여 과제로 넘기기 전에 사용자에게 먼저 제안한다.

### 짧은 생성자 호출의 줄바꿈 예외

아래는 사용자가 지정한 표현 기준이며, `development-guide.md`의 DTO, `record` 생성자 호출 줄바꿈 규칙과 해당 커밋 전 검증 기준보다 우선 적용한다.

- `Map.of`처럼 키와 값을 짝으로 나열할 때, 값이 짧고 단순한 DTO, `record` 생성자 호출이면 키와 생성자 호출을 한 줄에 함께 쓸 수 있다. 각 키, 값 쌍은 별도 줄에 둔다.
- 인자가 소수의 리터럴이나 짧은 변수이고 한눈에 의미를 파악할 수 있을 때 이 예외를 적용한다. 긴 표현식, 중첩 호출 또는 인자가 많아 읽기 어려운 경우에는 기존 줄바꿈 규칙을 따른다.
- 이 예외에 해당하는 코드를 커밋 전 검증에서 인자별 줄바꿈을 이유로 다시 펼치지 않는다. `record` 선언 자체의 컴포넌트별 줄바꿈 규칙은 유지한다.

```java
Map.of(
        42L, new ActivityCounts(2L, 7L),
        7L, new ActivityCounts(8L, 1L),
        99L, new ActivityCounts(1L, 0L)
)
```

## 1. 기본 원칙과 작업 방식

### 과도한 구현 지양

- 구현 범위는 확인된 요구사항과 구체적인 근거에 맞추고, 필요 이상의 기능, 구조를 추가하지 않는다.
- 미래 가능성만으로 인터페이스, 포트, 어댑터, 팩토리, 계층을 추가하지 않는다.
- 추상화는 의미 있는 시스템 경계, 복수 구현, 또는 분명한 테스트, 유지보수 이점이 있을 때 도입한다.
- 디자인 패턴 적용 자체를 목표로 하지 않는다.

### 풍부한 도메인 모델

- 비즈니스 규칙, 불변식, 상태 변경은 가능한 한 해당 도메인 객체가 책임진다.
- Service에 도메인 조건문과 상태 변경 로직을 몰아넣지 않는다.
- Entity의 상태는 범용 Setter보다 의도가 드러나는 행위 메서드로 변경한다.
- 규칙이 없는 단순 조회, 변환, 외부 API 연동을 위해 형식적인 도메인 객체를 만들지 않는다.

### 에이전트 자율성

- 단순하고 국소적인 변경은 관련 코드를 확인한 뒤 바로 수행한다.
- 새 도메인 정책, 프로젝트 전반의 아키텍처 변경, 팀 규칙 변경, 운영, 기술 스택에 큰 영향을 주는 의존성은 임의로 확정하지 않는다.
- 새로 작성하거나 직접 수정하는 코드는 이 가이드를 따르되, 현재 요청과 무관한 기존 코드를 컨벤션에 맞추려고 리팩터링하지 않는다.
- 관련 없는 코드 냄새나 스타일 문제는 수정하지 않는다. 심각한 버그, 보안 문제, 데이터 손상 가능성은 사용자에게 알린다.
- `development-guide.md`는 사용자의 명시적인 요청 없이 수정하지 않는다.

## 2. 프로젝트 구조와 의존 방향

패키지는 기능 중심으로 구성한다.

```text
book/
├── controller/
├── service/
├── domain/
├── repository/
├── client/
└── dto/
```

필요한 하위 패키지만 만든다. 기본 책임은 Controller의 HTTP 경계, Service의 유스케이스 조합과 트랜잭션 경계, Domain의 비즈니스 규칙, Repository의 영속성 접근, Client의 외부 통신이다.

- Service가 다른 Service를 직접 호출하지 않는다. 여러 도메인의 협력이 필요하면 해당 유스케이스를 책임지는 Service가 필요한 Domain, Repository, Client와 직접 협력하도록 설계한다.
- Repository는 기본적으로 Spring Data JPA 인터페이스를 직접 사용한다. 실제 필요 없이 별도의 Repository Port와 Adapter를 만들지 않는다.
- JPQL의 엔티티 별칭은 엔티티 이름과 겹치지 않도록 `Review r`, `Book b`처럼 짧고 분명하게 쓴다. 한 글자로 구분하기 어려우면 `re`처럼 의미가 드러나는 축약형을 쓴다.
- 외부 API Client는 기본적으로 구체 클래스를 직접 주입한다. 교체 요구나 복수 구현이 실제로 생기기 전에는 Client 인터페이스를 먼저 만들지 않는다.

## 3. Java와 객체 설계

- 객체지향 생활 체조는 책임, 가독성, 도메인 표현력을 높이는 범위에서 실용적으로 적용한다.
- 제어문 중첩 깊이는 최대 2로 제한한다. `else` 자체를 금지하지 않는다.
- 분기에서 유효하지 않은 입력이나 빈 결과를 처리하고 이후 작업을 건너뛰어야 할 때는 조기 반환한다.
- 분기 이후의 처리와 반환 형태가 같고 값 하나만 달라지면, 기본값을 지역 변수에 두고 `if`에서 갱신한 뒤 한 번 반환한다. `nextPage`의 `null` 여부처럼 API 의미가 있는 선택은 삼항 연산자로 숨기지 않는다.
- 메서드는 약 20줄을 소프트 가이드로 삼는다. 줄 수를 맞추기 위한 무의미한 private 메서드 추출은 하지 않는다.
- 일반 메서드 선언은 파라미터가 2~3개 정도이고 타입과 이름이 짧아 한눈에 읽히면 한 줄로 둔다. 줄바꿈이 필요하면 여는 `(` 바로 뒤에서 줄을 바꾸고 파라미터마다 한 줄을 사용하며, 닫는 `)`도 별도 줄에 둔다. 줄바꿈한 선언에서 파라미터 둘 이상을 같은 줄에 두지 않는다.
- `record` 선언은 컴포넌트마다 한 줄을 사용한다. 여는 `(` 다음 줄에 첫 컴포넌트를 쓰고 닫는 `)`는 별도 줄에 둔다. 길이나 컴포넌트 수를 이유로 같은 줄에 묶지 않는다.
- DTO, `record` 생성자 호출은 인자가 둘 이상이면 여는 `(` 다음 줄부터 인자마다 한 줄을 사용하고 닫는 `)`를 별도 줄에 둔다. `ResponseEntity.ok(new ...`처럼 다른 호출 안에 있어도 동일하다.
- 그 밖의 생성자, 메서드 호출은 한 줄에 들어가면 한 줄로 두되, 줄바꿈하면 인자마다 한 줄을 사용하고 닫는 `)`를 별도 줄에 둔다.

```java
return ResponseEntity.ok(new GuestInfoResponse(
        actor.getGuestNickname(),
        actor.getExpiresAt(),
        actor.getId(),
        actor.getType()
));

public record GuestInfoResponse(
        String nickname,
        LocalDateTime expiresAt,
        long actorId,
        ActorType actorType
) {
}
```

- 스트림 체인은 한 줄에 체인 메서드 호출 하나만 둔다. `.stream()`, `.map(...)`, `.toList()`처럼 점(`.`)으로 이어지는 각 호출을 별도 줄에 배치한다. 다른 호출의 인자로 쓰더라도 먼저 체인을 줄바꿈하고, 그래도 읽기 어렵거나 결과의 의미를 드러내야 할 때만 지역 변수로 분리한다.
- 타입은 `import`한 뒤 단순 클래스명으로 참조한다. 메서드 본문에서 `java.util.stream.Collectors.toMap(...)`처럼 패키지 전체 경로를 쓰지 않고, `import java.util.stream.Collectors;`와 `Collectors.toMap(...)`을 사용한다. 이름 충돌로 불가피할 때만 전체 경로를 사용한다.
- 원시값 포장과 일급 컬렉션은 도메인 의미나 불변식을 분명하게 만들 때만 사용한다.
- 내부 컬렉션은 외부에서 직접 수정할 수 없게 하고, 불변 복사본이나 읽기 전용 형태로 반환한다.

### Optional

- `Optional`은 조회 결과의 부재를 표현하는 반환 타입에 사용한다.
- Entity 필드, DTO 필드, 메서드 파라미터에는 사용하지 않는다.
- 필수값을 감싸거나 일반적인 분기, 제어 흐름을 대신하는 용도로 사용하지 않는다.

### 의존성 주입과 Lombok

- Spring Bean은 생성자 주입을 사용한다. 필요하면 `@RequiredArgsConstructor`를 사용한다.
- Domain과 Entity에는 `@Data` 또는 클래스 단위 `@Setter`를 사용하지 않는다.
- `@Builder`는 기본 선택이 아니며 생성 의도가 더 명확해질 때만 사용한다.

## 4. DTO, Validation, 트랜잭션

- ChaekChaek API DTO는 `Request`, `Response` suffix를 사용하고 기본적으로 Java `record`로 작성한다.
- 외부 API 요청, 응답 DTO와 ChaekChaek API DTO를 구분한다.
- Request는 null, blank, 형식 등 입력 경계의 검증을 담당한다.
- Domain은 허용 가능한 값 조합, 상태 전이 등 비즈니스 불변식을 검증한다.
- 단순 조회, 검색, 외부 API 변환처럼 별도 도메인 모델의 이점이 없는 경우 Service가 `Response` DTO를 반환할 수 있다.
- Service는 `ResponseEntity`, `HttpStatus`, Servlet API 등 HTTP 타입에 의존하지 않는다.
- 트랜잭션 경계는 Service에만 둔다. 쓰기는 `@Transactional`, 읽기는 `@Transactional(readOnly = true)`를 사용하며 Controller와 Domain에는 트랜잭션 annotation을 두지 않는다.

## 5. 예외 처리

- 비즈니스 예외의 최상위 타입은 `BusinessException`으로 한다. 필요하면 `BookException`과 같은 도메인별 중간 예외를 둔다.
- `BusinessException`은 애플리케이션 에러 코드와 사용자 메시지를 정의한 `ErrorCode`를 가진다.
- `ErrorCode`는 `HttpStatus`, `ProblemDetail` 등 HTTP 타입에 의존하지 않는다.
- `ApiExceptionHandler`가 예외를 HTTP 상태와 Spring `ProblemDetail`로 변환하고, 애플리케이션 에러 코드는 `code` 확장 필드로 제공한다.
- `InfrastructureException`에는 `ErrorCode` 보유를 강제하지 않으며 외부 API, I/O 등 실제 기술 원인을 `cause`로 보존한다.

## 6. 테스트와 API 문서

- 비즈니스 로직과 버그 수정은 가능하면 테스트를 먼저 작성한다. 모든 변경에 TDD를 강제하지는 않는다.
- 가능한 한 단위 테스트로 검증하고, Spring 경계 자체를 검증할 때만 Context를 사용한다.

```text
Domain      → JUnit + AssertJ
Service     → JUnit + AssertJ + Fake / Mockito
Controller  → @WebMvcTest + MockMvc + REST Docs
Repository  → @DataJpaTest
HTTP Client → MockWebServer
```

- 상태 기반 검증과 가독성에 유리하면 Fake를, 단순 협력이나 호출 검증에는 Mockito를 사용한다. Fake를 위해 프로덕션 코드에 불필요한 인터페이스를 만들지 않는다.
- 테스트를 추가하기 전에 관련 기존 테스트의 fixture, 시간 제어와 검증 방식을 확인하고, 같은 목적에는 기존 방식을 우선 사용한다.
- 시간 값이나 시간에 따른 동작을 검증할 때는 `Instant.now()` 등 실행 시점의 현재 시각 대신 `Instant.parse(...)`로 만든 고정 시각을 사용한다. 현재 시각을 한 번 구해 상수에 저장하는 것도 고정 시각을 대신하지 않는다. 서비스에는 `Clock.fixed(...)`를 주입하거나 mock `Clock`이 고정 시각을 반환하도록 설정하고, 시간 경과는 `plusSeconds(...)` 등으로 명시한다.
- DB 저장 전후의 시간 값이나 시간이 포함된 응답을 비교할 때는 DB 컬럼의 정밀도와 반올림을 확인한다. 정밀도 자체가 검증 대상이 아니면 초 단위처럼 저장 전후에 값이 유지되는 고정 시각을 사용한다. 정밀도 차이로 실패한다는 이유만으로 시간 필드를 비교에서 제외하거나 임의의 오차를 허용하지 않는다.
- 테스트 메서드명은 `should_ExpectedResult_When_Condition` 형식의 영어로 작성한다.
- `@DisplayName`은 한국어 `~다` 어투로 작성하고 마침표를 붙이지 않는다.
- 테스트 본문은 기본적으로 `// given`, `// when`, `// then`을 사용하며 필요하면 `// when & then`으로 합친다.
- 예외는 다음과 같이 구체 타입을 중심으로 검증한다.

```java
assertThatThrownBy(() -> subject.execute())
        .isInstanceOf(BookNotFoundException.class);
```

- 예외 메시지는 기본적으로 검증하지 않는다. 비즈니스 오류 구분이 중요하면 문자열보다 `ErrorCode`를 검증한다.
- API 문서는 Spring REST Docs와 Swagger/OpenAPI 연동 방식으로 관리한다. Controller 테스트가 API 동작과 REST Docs 생성을 함께 검증한다.

## 7. 코드 작성 규칙

### 메서드 배치

- public 메서드 바로 뒤에 그 메서드가 사용하는 private 메서드를 둔다.
- 여러 public 메서드가 공유하는 private 메서드는 관련 public 메서드들 뒤에 둔다.
- 그 밖에는 알파벳 순서를 기본으로 하되 CRUD 등 자연스러운 의미 순서가 있으면 이를 우선한다.

### 상수와 오류 메시지

- 상수를 전역 `Constants` 클래스나 enum에 모으지 않고 실제 사용 책임이 있는 클래스 가까이에 둔다.
- `NICKNAME_MAX_LENGTH`처럼 의미와 제한 조건이 드러나는 이름을 사용한다.
- 사용자 노출 오류 메시지는 금지 표현보다 기대 조건을 설명한다. 예: `이름은 10자 이하여야 합니다`.
- 부정 표현이 불가피하면 사용자가 다음에 취할 행동을 알 수 있게 작성한다.

### 의존성 추가

- JDK, Spring, 기존 라이브러리로 충분하면 단순 편의를 위한 의존성을 추가하지 않는다.
- 새 의존성이 문제를 실질적으로 해결할 때만 도입하고 필요성을 설명한다.
- 아키텍처나 운영에 큰 영향을 주는 의존성은 추가 전에 사용자에게 확인한다.

## 8. 구현 중, 커밋 전 검증

- 구현 중에는 변경 범위와 직접 관련된 최소한의 테스트를 실행한다. 실패 원인을 좁히는 데 필요한 테스트만 추가로 실행한다.
- 코드 변경을 커밋하기 직전에 `./gradlew test`로 전체 테스트를 한 번 실행한다. 구현 중간 단계에서 전체 테스트를 반복하지 않는다.
- 커밋 전 diff에서 새로 작성하거나 수정한 `record` 선언과 DTO, `record` 생성자 호출의 컴포넌트, 인자가 각각 한 줄인지 확인한다. 한 줄에 여러 값을 묶은 부분이 있으면 테스트 전에 고친다.
- 문서만 변경한 경우에는 전체 테스트 대신 변경한 문서의 내용과 형식을 확인한다.
- 테스트가 없는 변경도 필요하면 컴파일 또는 빌드로 검증한다.
- 실패한 테스트가 있는 상태에서 완료했다고 보고하지 않는다. 기존 실패라면 근거와 함께 명확히 알린다.
- 변경과 무관한 검증을 형식적으로 반복하지 않는다.

## 9. Git 작업 방식

- 작업 브랜치는 `be`를 기준으로 작업의 주된 목적에 맞는 prefix를 사용한다.
  - `feature/`: 기능 추가. 예: `feature/book-search`.
  - `fix/`: 버그 수정. 예: `fix/book-null-description`.
  - `refactor/`: 기존 동작을 유지하는 구조, 책임 정리. 예: `refactor/book-search`.
  - `style/`: import, 줄바꿈, 코드 배치 등 동작에 영향을 주지 않는 표현 정리. 예: `style/backend-code-conventions`.
- 여러 종류의 변경이 섞인 경우 브랜치 prefix는 작업의 주된 목적을 따르고, 각 커밋의 type은 해당 변경에 맞게 선택한다.
- 커밋 메시지는 AngularJS 스타일을 바탕으로 `[영역] type(scope): 설명` 형식을 사용한다.
- 영역은 `BE`, `FE`, `AN`, `ALL` 중에서 선택한다.
- 허용하는 type은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `build`, `perf`, `revert`, `style`이다.
- scope는 변경 대상을 명확히 할 때 사용하며 생략할 수 있다.

```text
[BE] build: 프로젝트 초기 세팅
[FE] feat(auth): 로그인 화면 구현
[AN] fix: 토큰 만료 처리 수정
[ALL] docs: 개발 환경 설정 안내 추가
```

### 커밋 단위 결정과 실행

- 구현 시작 전에 요구사항을 독립적으로 설명할 수 있는 동작, 정책, API 계약 변경으로 나누고, 각 단위의 목적, 관련 파일, 검증 방법, 예정 커밋 제목을 자신의 브랜치 작업 기록에 적는다. 작업 범위가 바뀌면 계획도 갱신한다.
- 같은 사용자 요청, 이슈, 도메인, Controller에 속한다는 이유만으로 한 커밋에 묶지 않는다. 같은 API의 변경이어도 공개 여부, 인증 방식, 요청, 응답 계약, URI 변경처럼 독립적으로 검토, 검증, 되돌릴 수 있는 목적은 별도 커밋으로 나눈다.
- 하나의 목적을 완성하는 프로덕션 코드, 테스트, REST Docs, OpenAPI 문서는 같은 커밋에 포함한다. 파일이나 계층, 코드, 테스트, 문서라는 종류만을 기준으로 쪼개지 않는다. 여러 API에 같은 정책을 적용하는 변경은 하나의 목적일 수 있다.
- 공통 코드 의존 때문에 나누기 어렵다면 먼저 독립적으로 검증 가능한 선행 변경을 분리한다. 서로 다른 목적을 꼭 함께 커밋해야 한다면, 분리 시 컴파일, 테스트 또는 API 계약이 깨지는 구체적인 이유를 작업 기록에 남긴다. 작업량이 적거나 수정 파일이 겹친다는 것은 합치는 근거가 아니다.

| 변경 예시 | 커밋 구분 |
| --- | --- |
| `GET` 추천 도서 조회의 관리자 권한 요구 제거 | 공개 조회 정책 변경으로 별도 커밋 |
| `POST`, `DELETE` 추천 도서의 쿠키 인증 지원 또는 기존 지원 검증 | 같은 인증 정책을 적용하는 두 API는 함께 묶되, `GET` 공개 변경과 분리 |
| 추천 도서 세 API의 URI를 같은 리소스 경로로 통일 | 세 API 경로와 보안 설정, Location, 테스트, 문서를 함께 묶되, 인증 정책 변경과 분리 |
| 커밋 방식 등 개발 지침 수정 | API 동작 변경과 별도 작업 단위로 처리 |

각 단위는 다음 순서로 완결한다. 전체 작업을 구현한 뒤 편의상 한 번에 커밋하지 않는다.

1. 계획한 한 단위를 구현하고 관련 테스트로 검증한다.
2. 해당 단위의 변경만 stage한 뒤 `git diff --cached` 전체를 읽는다. 계획한 목적에 모든 변경이 필요한지, 별도로 검증, 되돌릴 수 있는 다른 목적이 섞였는지, 커밋 제목이 실제 구현 또는 검증 범위를 정확히 나타내는지 확인한다. 같은 파일에 여러 목적이 섞였으면 변경 부분별로 stage한다.
3. 코드 변경은 전체 테스트, 문서만 변경한 경우는 내용, 형식을 검증한 뒤 사용자 확인 없이 즉시 커밋한다. 커밋 전 검증은 8절을 따른다.
4. 커밋을 마친 뒤 다음 변경 단위의 구현으로 넘어간다.

Git으로 관리하지 않는 로컬 지침, 작업 기록은 기존 untracked 정책을 유지하며, 내용, 형식 검토로 해당 작업 단위를 마친다.

- PR의 Squash and Merge를 전제로 작업 흐름과 리뷰가 이해되기 좋은 커밋 단위를 선택한다. 최종 Squash를 이유로 구현 중 서로 다른 목적을 합치지 않는다.
- 각 커밋은 가능한 한 관련 테스트가 통과하는 Green 상태로 만든다. TDD의 Red 단계는 작업 과정으로만 두고 실패하는 테스트만 담은 커밋은 만들지 않는다.

### 작업 상태와 변경 보호

- 작업 시작 시 worktree 상태를 확인하고 기존 사용자 변경을 수정, 삭제, 되돌리거나 에이전트 커밋에 포함하지 않는다.
- `git add .`와 `git add -A`를 기본적으로 사용하지 않고 에이전트가 변경한 파일만 명시적으로 stage한다.
- 같은 파일에 사용자 변경과 에이전트 변경이 섞여 안전하게 분리할 수 없으면 사용자에게 알린다.
- 명시적인 요청 없이 `reset --hard`, `checkout -- <file>` 등 파괴적인 Git 명령을 사용하지 않는다.
- `git push`는 자동으로 수행하지 않는다.

### 이슈와 PR 작성

- 이슈는 기본적으로 **현재 문제**와 **기대 결과**로 구성한다. 현재 문제에는 클라이언트나 사용자가 겪는 한계와 그 맥락을, 기대 결과에는 완료 후 확인할 수 있는 동작과 수용 조건을 적는다.
- 필요한 API 계약, 식별값의 의미, 기존 동작의 호환성은 기대 결과에 명시할 수 있다. 요구사항 자체가 특정 구현을 필요로 하지 않는 한 DTO 분리, 조회 방식, 계층 구조, 테스트, 문서 갱신 방법 등은 이슈에서 확정하지 않는다.
- 이슈를 생성할 때 본문과 함께 Assignees와 Labels를 설정한다. 사용자가 자신의 작업 이슈 작성을 요청하고 별도 담당자를 지정하지 않았다면 `HyoYoonNam`을 담당자로 지정한다. 다른 담당자가 명시되면 해당 계정을 사용하고, 담당자를 판단할 근거가 없으면 임의로 지정하지 않는다.
- Labels는 생성 전에 저장소의 실제 라벨을 확인해 영역과 작업 유형에 맞게 지정한다. 예를 들어 `[BE] feat:` 이슈에는 `BE`와 `✨ feat`를 적용한다. 존재하지 않는 라벨을 추측하거나 새로 만들지 않는다. 이슈 생성 후 담당자와 라벨이 의도대로 저장됐는지 확인한다.
- PR은 프로젝트 양식의 **관련 이슈**, **작업 내용**, **리뷰 포인트**, **참고 사항**을 채운다. 작업 내용에는 실제로 변경한 API, 동작과 영향 범위를, 리뷰 포인트에는 구현 선택의 이유와 검토한 대안의 장점, 비용을 적는다. 의미 있는 선택지가 있었다면 비교표를 사용할 수 있다. 참고 사항에는 실행한 검증 명령과 결과를 적는다.
- 이슈나 PR 본문에서 다른 이슈, PR 번호를 참조할 때는 참조마다 `- `로 시작하는 별도 Markdown 목록 항목을 사용한다. 예: `- Closes #407`, `- 후속 맥락: #379`. 줄만 바꾼 일반 문장이나 문장 안의 괄호로 참조를 나열하지 않는다.
- PR도 생성할 때 Assignees와 Labels를 함께 설정한다. 관련 이슈와 같은 담당자, 영역, 작업 유형을 기본으로 하되, 실제 PR의 작업 범위가 다르면 그에 맞춰 지정한다. 생성 후 대상 브랜치와 함께 담당자, 라벨이 의도대로 저장됐는지 확인한다.
- 이슈에 적혀 있던 구현 방향이나 대안 비교를 나중에 이슈에서 덜어낼 때는 그 내용을 PR로 옮겨 선택의 맥락을 보존한다. 짧은 결론만 남기고 근거를 버리지 않는다.
- 작성 예시는 [GA4 사용자 식별값 이슈 #379](https://github.com/woowacourse-teams/2026-chaekchaek/issues/379)와 [구현 PR #387](https://github.com/woowacourse-teams/2026-chaekchaek/pull/387)을 참고한다.

### AI 작업 시간 기록

- AI 작업 시간의 기준 기록은 `docs/ai/work-logs/<branch-name>.md`다. Git commit trailer는
  작업 시간 기록 용도로 사용하지 않는다. 브랜치별 파일을 사용해 병렬 worktree 작업에서
  같은 파일을 동시에 수정하지 않게 한다.
- 에이전트는 작업을 시작하기 전에 자신의 브랜치 작업 기록 파일에 시작 시각과 작업 범위를
  기록하고, 논리적으로 완결된 변경을 커밋한 직후 종료 시각, 실제 작업 시간, 브랜치,
  커밋 해시, 검증 결과를 같은 항목에 보완한다.
- 새 작업 항목은 문서의 템플릿을 그대로 사용한다. `date -Iseconds`로 ISO 8601 시각을
  확인하고, 커밋 후에는 `git rev-parse HEAD`와 실제 실행한 검증 명령의 결과를 기록한다.
- 커밋하기 전에는 해당 작업 항목에 종료 시각과 `AI-Duration`이 모두 있는지 확인한다.
  커밋 후에는 `git diff --check`와 함께 자신의 작업 기록 파일 변경도 검토한다.
- 작업 기록 파일은 로컬 작업 이력이다. 반드시 untracked 상태로 두며, stage 또는 commit하지
  않고 `.gitignore`에도 추가하지 않는다.
- 작업 시간에는 코드 탐색, 설계, 구현, 테스트, 디버깅, 검증 등 해당 커밋을 완성하기 위해 수행한 작업을 포함한다.
- 사용자 응답을 기다리는 시간은 작업 시간에서 제외한다.
- 시작과 종료 시각은 ISO 8601 형식으로 기록한다.
- `AI-Duration`에는 사용자 대기 시간을 제외한 실제 작업 시간을 기록한다.

`docs/ai/work-logs/feature-book-resolve.md` 예:

```md
## 2026-08-14 — feature/book-resolve

- Scope: ISBN13 기반 책 resolve 구현
- AI-Started-At: 2026-08-14T00:41:23+09:00
- AI-Finished-At: 2026-08-14T00:54:12+09:00
- AI-Duration: 12m49s
- Commit: `abc1234`
- Verification: `./gradlew test --tests ...` 통과
```

템플릿:

```md
## YYYY-MM-DD — <branch-name>

- Scope: <작업 범위>
- AI-Started-At: <ISO 8601>
- AI-Finished-At: <ISO 8601>
- AI-Duration: <실제 작업 시간>
- Commit: `<commit hash>`
- Verification: <실행한 명령과 결과>
```

기존 커밋의 trailer 형식은 이력을 보존하며 수정하지 않는다.

이전 trailer 형식의 예:

```text
AI-Started-At: 2026-08-14T00:41:23+09:00
AI-Finished-At: 2026-08-14T00:54:12+09:00
AI-Duration: 12m49s
```

## 10. 의사결정과 컨벤션 후보

### `docs/decisions`

- 구현 중 나중에 선택 근거를 다시 확인할 가치가 있는 중요한 기술적 분기만 `docs/decisions/<decision-name>.md`에 기록한다.
- 파일명은 날짜 없는 kebab-case를 사용하고 문서는 `Context`, `Options`, `Decision`, `Rationale`을 간결하게 담는다.
- 현재 작업과 관련된 기존 문서는 필요할 때 참고할 수 있다.

### `docs/convention-candidates`

- 반복적으로 나타나 향후 팀 규칙으로 검토할 가치가 있는 패턴만 `docs/convention-candidates/<candidate-name>.md`에 기록한다.
- 이 디렉터리는 사람의 검토를 위한 수집함이다. 에이전트는 기본적으로 읽지 않고, 내용을 현재 규칙으로 적용하거나 스스로 확정 규칙으로 승격하지 않는다.

### 공통 추적 규칙

- `docs/decisions/*`, `docs/convention-candidates/*`, `docs/ai/work-logs/*`는 untracked 상태로 유지한다.
- 두 디렉터리의 파일을 stage하거나 commit하지 않는다.
- untracked 상태를 숨기기 위해 `.gitignore` 또는 다른 ignore 설정을 변경하지 않는다.

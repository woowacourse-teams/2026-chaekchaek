# 책췍 강제 업데이트 운영과 검증

먼저 저장소 루트의 `docs/mobile-remote-config-updates.md`를 읽는다. 스킬 경로에서 루트는 `../../..`이다. 정책 스키마, 적용 시점과 검증 이력의 원본은 해당 문서이며 과거 임시 파일에 의존하지 않는다.

## 대상과 권한

- 현재 작업 트리, 커밋과 추적 변경을 확인한다. 이 기능을 완성하는 후속 검증은 기존 기능 브랜치를 재사용하며, 설치·조회만으로 새 브랜치를 만들지 않는다.
- 사용 가능한 Firebase 전용 MCP를 먼저 확인한다. 제공되지 않거나 접근 불가라면 사유를 알리고 공식 Firebase Remote Config 스킬과 CLI를 사용한다.
- Firebase 계정과 프로젝트를 명시적으로 확인한다. CLI 기본 계정이 책췍 계정이라고 가정하지 않는다. 운영 연결의 알려진 프로젝트는 `chaekchaek-d2b85`, 매개변수는 `mobile_policy_v1`이다. Android Debug는 별도 프로젝트이므로 운영 수신 검증에 섞지 않는다. 실제 빌드의 연결을 다시 확인한다.
- 변경할 값, 대상 사용자 범위, 복구할 기존 값과 테스트/상시 운영 여부를 제시하고 게시 승인을 받는다. 현재 대화에서 승인된 동일 변경과 복원은 재승인을 요구하지 않는다. 과거 승인을 새로운 세션의 게시 권한으로 재사용하지 않는다.
- 상시 운영에서는 대상 사용자가 스토어에서 실제 새 버전을 설치할 수 있는지 먼저 확인한다. 의도적인 테스트라면 새 바이너리 없는 차단이라는 점을 검토에 포함하고 복원까지 승인받는다.

## 게시 전 기기 준비

사용자가 물리기기를 지정하면 그 기기를 사용한다. 현재 Android/iOS 검증 스킬과 저장소의 실행 경로를 따른다. 명시적으로 허용된 로컬 Android는 공용 모바일 대기열 안에서 수행하고 명시적 serial을 사용한다.

1. 정확한 커밋의 APK와 설치된 앱의 패키지, 버전과 인증서 SHA-256을 비교한다. 일치하는 서명과 허용 버전일 때 `adb install -r`로 데이터를 유지한다. 삭제, 초기화나 강제 다운그레이드를 자동 대안으로 쓰지 않는다.
2. 기존 앱이 로컬 Debug 키라면 운영 Firebase에 연결된 검증용 Release 빌드만 같은 로컬 키로 서명하는 방법을 사용할 수 있다. 임시 빌드 설정으로 격리하고 스토어 서명 검증과 구분한다. 다른 서명 키를 사용할 수 없다면 설치를 멈추고 원인을 알린다.
3. 설치 검사 도구가 실패하면 원인을 확인한다. 예를 들어 apksigner 출력이 `V2 Signer: certificate SHA-256 digest:`이면 `Signer #1 certificate`만 읽는 파서가 실패할 수 있다. 서명 검증을 생략하지 말고 도구 원본 결과로 비교한다.
4. 기기 잠금을 사용자가 해제하고 실제 앱 화면이 보이는지 확인한다. 앱이 foreground에서 정상 동작하고, 현재 강제 팝업이 없다는 기준 화면을 확보한 뒤 게시한다. 잠금·연결·설치 문제를 해결하는 동안 운영 차단값을 올려두지 않는다.

## 제한된 게시와 원복

- 게시 직전 전체 템플릿을 새로 받아 비공개 작업 디렉터리에 원본을 보관한다. 검토한 기존 정책과 다르면 중단하고 새 diff를 검토한다. 키나 토큰은 출력·문서·커밋에 넣지 않는다.
- 최소/최신 값은 하나의 JSON 정책으로 함께 바꾸고 원본 템플릿의 다른 매개변수와 조건을 보존한다. Android는 versionCode 정수, iOS는 숫자 버전 문자열이며 최신은 최소 이상이어야 한다.
- 일시 테스트에는 게시 프로세스와 독립적인 기기 검증을 준비한다. 게시를 시도한 뒤에는 예외나 수신 실패에서도 `finally` 경로로 복원을 시도하고, 명시적 복원 신호와 제한 시간을 둔다. 이번에 사용한 예시는 게시 확인 후 최대 90초였다. 고정 운영 SLA로 일반화하지 않는다.
- 게시 후 서버 템플릿을 다시 받아 의도한 값과 일치하는지 확인한다. 서버 게시 성공만으로 앱 수신 성공이라고 보고하지 않는다.
- 테스트 종료 즉시 복원한다. 복원 직전 템플릿을 다시 읽어 다른 매개변수의 동시 변경을 보존하고, 자신이 수정한 정책만 원래 값으로 되돌린다. 같은 정책을 다른 사람이 바꿨다면 덮어쓰지 말고 충돌과 현재 차단 상태를 즉시 알린다.
- 복원 후 서버 재조회와 버전 이력을 확인한다. 원복 실패 시 차단이 해제됐다고 보고하거나 조용히 종료하지 않는다. 앱이 복원 정책을 받았는지도 별도로 확인한다. 오프라인에서는 이전 차단이 남을 수 있다.

## 앱 증거와 판정

- 실제 수신으로 `업데이트가 필요해요`, 본문과 `업데이트` 단일 버튼이 표시되고 `나중에`가 없는지 화면 구조와 캡처로 확인한다. 앱을 재시작했는지, 게시/서버 확인/화면 관측의 측정 기준이 무엇인지 기록한다.
- 뒤로가기와 외부 영역 탭으로 닫히지 않는지 확인한다. 이 조작은 사용자 터치와 겹치지 않게 한다. 수동 터치로 Play 전환이 캡처됐다면 팝업 전체 캡처나 독립적인 뒤로가기 검증으로 판정하지 않는다. 필요하면 이미 확보한 화면 구조와 제한을 기록한다.
- 복원 후 앱이 foreground에서 정책을 받아 팝업이 사라지고 기존 화면을 이용할 수 있는지 확인한다. 앱 데이터 초기화나 SDK 캐시 삭제로 원복 수신 검증을 대신하지 않는다.
- 원격 게시, 서버 재조회, Android 앱 수신, iOS 앱 수신, Play Flexible/Immediate 실제 설치, App Store 설치를 각각 구분한다. `adb install -r`, 개발자 임시 덮어쓰기나 FakeAppUpdateManager 성공은 실제 스토어 설치 증거가 아니다.
- 결과에 소스 커밋, 빌드/서명 방식, 기기, 정책 diff, 게시·복원 버전과 시각, 앱 증거, 미확인 범위를 남긴다. 검증 문서는 기존 원본에 갱신하고 커밋한다. 자신이 획득한 검증 슬롯을 반환하되 사용자 물리기기를 종료하지 않는다.

## 재사용할 때 다시 확인할 값

2026-10-23 사례는 앱 `1.3.1 (10)`에 Android 최소/최신 11과 iOS 최소/최신 1.3.2를 게시한 뒤 기존 모두 0인 정책으로 복원했다. 이것은 과거 검증값이다. 다음 실행에서 현재 버전, 기존 정책, 서명, serial, 계정이나 허용 시간을 그대로 가정하지 않는다. 상세 근거와 당시 커밋은 원본 문서를 확인한다.

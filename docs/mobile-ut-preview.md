## 앱 반영과 구분

검색 중복 ISBN 제거, 출발 책장 직접 저장 ViewModel과 온보딩 등 일부 입력의 키보드 닫기는 앱에 반영되어 있다. 검색 명칭, 피드와 검색 TOP, 책장 담기에서 검색으로 이동하는 UI 연결, 별점 드래그, 감상 진입 문구와 키보드 닫기를 Android/iOS 공통 코드에 반영했다. 검색에서 연 상세의 담기도 출발 책장으로 이어지며 해당 경로에서는 다른 책장에 담기 메뉴를 숨긴다. 일반 진입의 책장 선택은 유지한다. 웹과 서버 변경은 범위 밖이다.

Android UI 트리에서 기존 Compose 테스트 태그를 안정적으로 조회하도록 Android 호스트에 리소스 ID 노출을 추가했다. 이는 기존 태그를 노출하는 변경이며 iOS의 공통 UI나 기능 의미를 바꾸지 않는다.

## HTML 검토와 기존 검증

- Android host 테스트 495개, Debug APK와 AndroidTest APK 빌드 통과. Pixel 6a API 33에서 동일 버전 1.3.1(10), 동일 서명을 확인하고 데이터를 보존해 설치했다.
- 온보딩 화면 fixture의 실제 탭과 네이티브 키 입력으로 빈 영역 탭 후 포커스 해제, 입력칸 재진입 3회, IME 검색 후 포커스 해제와 검색어 보존 테스트 1개가 통과했다. 실제 계정과 온보딩 저장 상태를 초기화하지 않았다. 이 테스트는 포커스와 내용 보존을 검증하며 별도의 키보드 표시 상태 검사는 없다.
- Jev의 홈에서 발견 탭 이동은 1단계로 통과했다. 후속 검색 시나리오는 빈 검색창 탭 이후 앱의 MotionEvent 응답 지연 ANR로 중단됐다. `archi` 입력 전 발생했으며 제보된 검색 크래시와 같은 원인인지는 미확인이다. ANR 당시 메인 스택은 `nativePollOnce`였고 원인은 특정하지 못했다. 기기 데이터는 지우지 않았다.
- 기존 게스트 상태로는 책장과 닉네임 변경에 진입할 수 없어 해당 실제 계정 경로와 저장 완료는 미검증이다. iOS는 이전 `93f3c76b`의 키보드 테스트 근거를 유지하며 이번 Android 전용 태그 노출과 HTML 작업으로 새 실행을 주장하지 않는다.
- HTML 390px, 320px에서 화면을 확인했다. 출발 책장 직접 담기 왕복, 중복 없는 제목 검색 결과, 별점 포인터 드래그, 입력 포커스 해제와 내용 보존, 상세 TOP 복귀 및 가로 넘침 없음을 확인했다.

## 승인 후 앱 구현과 ANR 조사

- 책장 검색 문맥은 회원, 책장 ID와 명시 로그아웃 세대를 보존한다. 동일 회원 재인증, 저장 실패와 재시도에서는 출발 책장을 유지한다. 다른 탭, 명시 로그아웃과 탈퇴는 해제한다. 다른 계정 또는 삭제된 대상에 최근 책장으로 대체 저장하지 않는다.
- 피드, 검색과 상세는 공통 TOP 컴포넌트를 사용한다. 별점은 0.5-5점 가로 드래그로 초안만 바꾸고, 세로 동작은 시트 스크롤에 맡긴다. 0점은 기존 개발 프리뷰 전용 옵션을 유지한다.
- 감상과 답글은 `키보드 닫기`, 한 줄 입력은 IME 완료, 입력 밖 탭은 공통 포커스 해제를 사용한다. 입력 안 탭과 재진입은 제외 가드로 보호하며 본문 개행과 초안을 보존한다.

ANR은 이전 APK `bb5dcdc301e2ff8f6754020d089aff34dd97b06e`, SHA-256 `32cb86c33ff7865fe9f18d7f10ff810c0160ce6d3176668b9798be639c8ac1ad`를 고정해 같은 Pixel 6a API 33 AVD에서 조사했다.

| 조건 | 관찰 | 판단 경계 |
| --- | --- | --- |
| 최초 ANR | MotionEvent 5001ms 지연. 시스템 memory pressure `some avg10=53.98`, `full avg10=15.58`, `kswapd0` CPU 41%. 앱 메인 스택은 수집 시 `nativePollOnce` | 시스템 메모리 압박은 확인됐으나 앱 내부 원인과 최초 UT 크래시의 동일 원인은 미확정 |
| 같은 APK, 4GB 콜드 부팅 | 검색창 탭, `archi` 입력 검증과 IME 제출 후 결과 57건 표시. 부팅 이후 ANR 없음. Jev는 이전 9건 조건으로 최종 판정을 중단 | 시나리오 통과로 기록하지 않는다. 앱 코드 변경으로 ANR이 해결됐다는 근거가 아니다 |
| 같은 APK, 2GB 콜드 부팅 | 현재 응답 57건 조건으로 Jev 5단계 통과. 부팅 이후 ANR 없음 | RAM 크기만을 근본 원인으로 확정할 수 없다 |

두 비교는 기존 AVD의 데이터와 서명을 유지했고 `-no-snapshot-load -no-snapshot-save`로 콜드 부팅했다. 새 앱 검증은 같은 AVD에 4GB를 임시 지정해 수행한다. 영구 AVD 설정이나 사용자 앱 데이터는 변경하지 않는다. 최초 로그에 비춰 시스템 압박이 유력하지만 재현되지 않는 앱 내부 정지 원인을 추정 코드로 덮지 않는다.

## 물리 Android 수동 테스트 (2026-11-06)

대상은 통합 PR #676의 앱 소스 `03552abb7fb1a1ea3d0f42ac7c71348b7f47d8be`, production API다. 실기기 설치용은 사용자가 교체를 승인한 릴리스 키 서명의 Debug `1.3.2-ut675(12)`이며 저장소 기본 버전은 변경하지 않았다. 아래 케이스는 사용자가 직접 실행할 절차이며 기존 에뮬레이터와 Simulator 통과 결과를 실기기 통과로 옮기지 않는다.

### 설치 상태와 준비

- 최초 두 차례는 기기 미연결로 대기했다. 이후 사용자 연결 승인으로 Galaxy S25 `SM-S931N`, Android 17, serial `R3CY709C7BD`를 확인했다.
- 설치본 `1.3.2(12)`는 릴리스 키 서명이고 PR 기본 APK `1.3.1(10)`는 디버그 키 서명이어서 첫 설치 검사를 차단했다. 사용자가 UT 코드 교체를 승인한 뒤, 저장소 밖 Gradle init 설정으로 versionName `1.3.2-ut675`, versionCode `12`, 기존 릴리스 키 서명을 적용했다. 제품 코드와 저장소 기본 버전은 변경하지 않았다. 이 테스트 표기는 설치본의 최신 기능을 모두 포함한다는 뜻이 아니다.
- 빌드 기준 HEAD는 문서 변경을 포함한 `04f4aa07f4ec50fb330b1096b9c0e525bd1e03c0`이다. `:app:verifyReleaseSigning :app:assembleDebug -PapiEnvironment=production`을 공용 대기열 안에서 실행했다. 워크트리에 없던 로컬 서명 설정은 기존 설정을 임시 연결하고 종료 시 제거했으며 저장소에 포함하지 않았다.
- 설치 전 검사는 동일 패키지, 동일 versionCode `12`, 동일 인증서 SHA-256 `a0a10d8cc1245dc95f1468aa034d68595ca54df4972621fc97680234bc0ddb53`으로 통과했다. APK SHA-256은 `413bd0fd84babd0a884b5fadb465436edd16f216194df5c81ffb87e33e9ef541`이다. `adb install -r`가 `Success`, MainActivity 시작이 `Status: ok`를 반환했다. 설치 후 재검사에서 설치본도 `1.3.2-ut675(12)`와 같은 인증서로 확인했다. 프로세스 실행, HOT 시작과 Window의 `mCurrentFocus`, `mFocusedApp`이 모두 책췍 MainActivity를 가리키는 것을 확인했다.
- 사용자가 앱이 없거나 실행되지 않는다고 재확인을 요청해 같은 기기에서 다시 빌드하고 교체 설치했다. 재설치 직전 설치본도 `1.3.2-ut675(12)`였으며 동일 서명·버전 검사와 `install -r`가 다시 성공했다. 빌드 기준 HEAD는 문서 변경을 포함한 `bb2c29a7f029394afebb0a56dbc813fcf51280f5`이고 APK SHA-256은 위와 동일하다. 일반 사용자 0에서 `installed=true`, `hidden=false`, `suspended=false`, `enabled=0`과 MAIN/LAUNCHER 실행 항목을 조회했다. MainActivity를 런처 action/category로 명시 실행한 후 프로세스·전경 창·실제 캡처에서 홈과 하단 `검색` 문구를 확인했다. 패키지만 지정한 암시적 실행 명령은 resolve 실패로 구분하며 이를 앱 미설치 근거로 사용하지 않는다. 사용자가 겪은 아이콘 부재 또는 실행 실패의 원인 자체는 확정하지 않았다.
- 설치 완료와 아래 수동 테스트 실행은 별개다. 15개 케이스는 모두 미실행이며 실제 로그인 유지와 운영 서버 저장 완료도 아직 확인하지 않았다.
- 기존 앱과 로그인·서재 데이터를 유지한다. 앱 삭제, 데이터 초기화, 강제 다운그레이드와 테스트용 게스트 초기화를 사용하지 않는다.
- 로그인한 계정에서 테스트용 책장 A, B를 준비하고 담기 전 두 책장의 목록을 확인한다. 담기와 감상 제출은 실제 서버 데이터를 변경하므로 테스트용 책과 문구를 사용한다.
- 결과는 `통과 / 실패 / 조건 미충족`으로 기록한다. 실행하지 않은 케이스의 초기 상태는 모두 `대기`다. 재시도나 특정 이미지 실패를 만들 수 없다면 해당 조건을 미검증으로 남긴다.

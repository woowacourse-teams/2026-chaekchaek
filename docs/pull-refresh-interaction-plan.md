# 새로고침과 목록 끝 상태 설계

2026-10-16 작성. 목적은 홈, 피드, 발견, 내 서재의 당겨서 새로고침과 하단 피드백을 Figma 상태와 구현 단위로 연결하는 것이다. 앱 구현 전 설계안이며 사용자 최종 디자인 승인, 빌드, 기기 검증을 뜻하지 않는다.

## 구현 추적

- 작업 브랜치: `529-pull-refresh-boundaries`. 기준은 출처 갱신이 반영된 `origin/an-develop`의 `3f305037`이다.
- 현재 단계: 구현 착수 준비. 이슈 생성과 작업 브랜치 준비를 마쳤으며 Draft PR 생성은 별도 승인 후 진행한다. 앱 코드 변경과 Android·iOS 검증은 아직 수행하지 않았다.

## 확정 범위

- 맨 위에서 아래로 당겨 현재 화면의 데이터를 다시 조회한다. 기존 내용과 검색 입력, 제출 검색어, 정렬, 필터는 요청 중과 실패 후에도 유지한다.
- 콘텐츠가 없거나 화면보다 짧아도 위쪽 당김이 가능하다.
- 맨 아래에서는 콘텐츠가 살짝 당겨졌다 돌아오며 추가 로딩 또는 데이터 끝을 표시한다. 헤더, 탭 바, 홈의 읽는 중 바는 고정한다.
- 사용자가 기존 페이지네이션 유지를 선택했다. 새 페이지네이션은 추가하지 않는다.
- 내 서재 편집 모드에서는 당겨서 새로고침을 비활성화한다. 편집을 끝내면 다시 사용할 수 있다.

### 상단 인디케이터

메인 컴포넌트 세트 [책췍/PullRefresh](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=1184-428)는 디자인 시스템 섹션 `1201:826`의 메인 컴포넌트 영역 `1196:1623`에 등록되어 있다.

| 상태 | 표현 | 동작 |
| --- | --- | --- |
| Idle | 숨김 | 당김 전 상태 |
| Pulling | 원형 진행 윤곽과 아래 화살표, 당겨서 새로고침 | 거리와 함께 점차 드러남. 임계점 전에 놓으면 요청 없이 복귀 |
| Ready | 거의 찬 원과 위 화살표, 놓으면 새로고침 | 임계점 도달. 놓으면 요청 시작 |
| Pending | 정지된 요청 표시, 갱신 요청 중 | 요청은 진행 중으로 잠금. 500ms 이전에는 회전 표시 없음 |
| Refreshing | 기존 Inline progress와 새로고침 중이에요 | 500ms를 넘긴 요청에 회전 표시. 응답 즉시 접힘 |
| Success / Error | 공통 인디케이터 접힘 | 성공은 데이터 교체. 실패는 기존 내용과 비차단 오류, 다시 시도 유지 |

상단 노출 영역과 임계점은 시안값 64pt다. 로딩 벡터는 기존 `Loading/Inline progress` 메인 `1058:411`의 20 x 20 인스턴스다. 첫 조회의 전체 로딩 화면과 갱신 중 상단 표시를 분리한다.

### 하단 당김과 상태

메인 컴포넌트 세트 [책췍/ListBoundary](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=1184-441)를 등록했다.

| 상태 | 표현 | 동작 |
| --- | --- | --- |
| Pending | 다음 내용을 요청하고 있어요 | 기존 추가 조회 조건이 충족되면 요청. 중복 호출 금지 |
| Loading | 기존 Inline progress와 더 불러오는 중이에요 | 500ms 이후 마지막 항목 아래에서 표시 |
| End | 여기까지 모두 봤어요 | 다음 페이지 요청 없음 |
| Error | 불러오지 못했어요와 다시 시도 | 기존 항목과 커서 유지. 사용자 재시도 전 자동 반복 금지 |

하단 콘텐츠 이동은 시안값 최대 24pt, 놓은 뒤 복귀는 220ms Ease out이다. 헤더와 탭 바는 움직이지 않는다. Android 기본 overscroll과 별도 효과가 겹쳐 두 번 움직이지 않게 한다. 짧은 목록과 빈 화면에서는 상단 갱신을 지원하되 존재하지 않는 다음 페이지를 요청하지 않는다.

프로토타입은 상단 Idle, Pulling, Ready, Pending, Refreshing의 5개 프레임과 하단 정지, 당김의 2개 프레임에 연결했다. 상단 Pending 이후 500ms 전이, 하단 release 후 220ms 복귀를 명세했다. 상단 완료 복귀는 클릭으로 표현하며 실제 API 응답 시간을 모사한 것은 아니다. 연속적인 손가락 저항감과 인디케이터 회전은 앱 구현 후 기기에서 확인해야 한다.

## 화면별 연결

코드 조사 기준은 `origin/an-develop`의 `ad6280a20886d4758274c2db61de56d8dec48a5a`다. 아래 소스 경로는 `android/shared/src/commonMain/kotlin/com/chaekchaek/app/` 기준이다.

| 화면 | 현재 조회 | 상단 갱신 | 하단 |
| --- | --- | --- | --- |
| 홈 | `HomeViewModel` -> `PopularBooksRemoteRepository.homeFeed()` | 홈 데이터 갱신. 읽는 중 바 유지 | 화면 페이지네이션이 없어 끝 표시 |
| 피드 | `FeedViewModel` -> `ReviewFeedRemoteRepository.reviewFeed(page, viewer)` | 감상과 스포일러 공개 상태 유지 | `nextPage`가 있으면 기존 sentinel 자동 조회, 없으면 끝 |
| 발견 기본 | `SearchRoute` Idle -> `DiscoverLanding` -> 공용 `HomeViewModel` | 추천 데이터 갱신. 입력과 최근 검색어 유지 | 화면 페이지네이션이 없어 끝 표시 |
| 발견 검색 | `SearchViewModel` -> `BookSearchRemoteRepository.search(query, sort, page)` | 마지막 제출 검색어와 현재 정렬로 갱신. 미제출 입력 유지 | `nextPage`가 있으면 기존 sentinel 자동 조회, 없으면 끝 |
| 내 서재 | `ArchiveViewModel` -> `LibraryRemoteRepository.getAll(token)` | 독서 상태 필터, 정렬, 책등 토글 유지 | repository가 모든 API 페이지를 읽으므로 화면은 끝 표시 |

검색 결과 없음과 서재 필터 결과 없음도 같은 조회 조건으로 갱신한다. 비로그인 서재는 현재 토큰이 없어 조회하지 않는다. 당김을 새 로그인 흐름으로 바꾸거나 서버 재조회 성공으로 표시하지 않는다. Figma의 빈 서재 예시는 로그인 후 항목이 없거나 필터 결과가 없는 경우다.

## 구현 순서

1. **조회 상태 분리**: 첫 조회와 `refresh()`를 구분한다. 기존 Content 또는 Empty를 유지하면서 요청 진행, 인디케이터 노출, 갱신 오류를 별도로 관리한다. 현재 `retry()`의 전체 Loading/Failure 전환을 그대로 호출하지 않는다.
2. **공통 제스처와 표시**: 화면 높이 이상인 스크롤 컨테이너로 빈 화면도 당김을 받게 한다. 상단 단계, 하단 저항과 복귀, 상태 footer를 연결한다. 현재 Compose 의존성에서 지원하는 표준 API를 확인해 선택한다.
3. **화면과 요청 경계 연결**: 기존 검색과 필터, 페이지네이션, 인증 경계와 연결한다. 아래 경쟁 요청과 내 서재 쓰기 경계를 처리한다.
4. **회귀 검증**: ViewModel의 요청과 상태 테스트 후 Android와 iOS에서 같은 시나리오로 거리, 저항, 고정 바, 접근성을 확인한다. 공통 코드와 플랫폼별 연결을 함께 확인하고 결과는 플랫폼별로 보고한다. Figma 시안값은 기기 검증으로 조정할 수 있다.

### 요청과 상태 보존

- 요청 진행 여부와 회전 표시 여부를 구별한다. 0-499ms에도 중복 요청을 막는다. 회전 표시는 500ms 이후, 응답 직후 종료하며 최소 노출 시간은 두지 않는다.
- 같은 화면의 반복 당김은 요청 한 건으로 제한한다. 공용 HomeViewModel을 사용하는 홈과 발견 기본도 동일 요청을 중복 실행하지 않는다.
- 갱신 시작 시 이전 추가 조회를 취소하거나 응답을 무효화한다. 갱신 중 새 추가 조회를 막고, 성공 후 새 커서만 사용한다. 실패 시 기존 커서를 유지한다.
- 검색어, 정렬, 인증이 달라진 뒤 도착한 응답은 최신 결과를 덮지 못하게 요청 세대와 입력 snapshot을 확인한다.
- 구현안은 피드와 검색에서 이미 읽은 페이지 범위를 다시 조회한 뒤 원자적으로 교체하는 것이다. 새 데이터가 일찍 끝나면 새 끝을 따른다. 중간 페이지 실패 시 기존 목록을 유지해 새 첫 페이지와 오래된 다음 페이지가 섞이지 않게 한다. 이 범위 보존 방식은 구현안이며 사용자 확정 요구와 구분한다.
- 검색 입력 `query`와 제출 검색어 `currentQuery`를 유지한다. refresh가 `search(query)`를 호출해 미제출 검색을 실행하거나 최근 검색어 순서를 바꾸거나 `cc_search_submit`을 다시 기록하지 않게 한다.
- 홈과 내 서재의 탭 재선택은 기존 맨 위 이동을 유지한다. 서버 목록을 SavedState에 저장하지 않고 기존 검색어, 정렬, 페이지 복원 단서를 사용한다.
- 서재의 조회와 쓰기가 공유하는 `libraryJob`을 확인한다. 갱신이 삭제와 독서 상태 변경을 취소하면 안 된다. 조회와 쓰기를 직렬화하거나 작업을 분리하고 쓰기 후 최신 목록을 반영한다. 사용자 확정 정책은 편집 모드에서 당겨서 새로고침을 비활성화하는 것이다. 편집 진입 시 진행 중인 당김을 접고, 편집을 끝낸 뒤 다시 허용한다. 삭제와 독서 상태 변경의 기존 선택 및 요청 흐름을 유지한다.
- 실패 시 기존 내용 또는 빈 상태를 보존하고 비차단 오류와 재시도를 표시한다. 추가 조회 실패를 데이터 끝으로 처리하지 않는다.

## 검증 계획과 현재 확인 범위

추후 자동 검증:

- 내용 있음과 빈 상태의 갱신 성공, 실패, 499ms/500ms 표시 경계, 반복 당김 호출 수.
- `nextPage == null`의 무요청, 추가 조회 실패와 재시도, ID 중복 제거.
- 갱신과 추가 조회 역순 응답, 검색과 정렬 변경, 로그인과 로그아웃, 취소 후 상태 해제.
- 미제출 입력과 제출 검색어가 다른 경우, 최근 검색어와 검색 제출 이벤트 중복 방지.
- 서재 필터, 정렬, 책등 토글과 선택 유지, 삭제나 상태 변경 도중 갱신.

추후 기기 검증:

- 네 화면의 긴 목록, 짧은 목록, 빈 화면에서 상단 당김과 임계점 전 취소, 임계점 후 release.
- 하단 로딩, 끝, 실패와 재시도, 24pt 이동과 220ms 복귀의 실제 손가락 감각.
- 고정 바와 알림 겹침, 가로 책 목록과 세로 당김 충돌, 큰 글꼴, TalkBack, 모션 감소.
- Android 실행 시 전역 에뮬레이터 lease와 명시적 serial 사용.
- iOS에서도 긴 목록, 빈 상태, 실패, 검색과 필터 유지, 고정 바를 같은 시나리오로 확인한다. VoiceOver와 모션 감소를 포함하며 Android 결과를 iOS 동작 증거로 대신하지 않는다.

이번에 확인한 범위는 Figma 16개 상태 화면과 공통 레퍼런스 캡처, 15개 인디케이터 인스턴스의 메인 연결, 제품 글꼴, 탭 바 위치, 오류 알림과 고정 읽는 중 바의 겹침이다. 프로토타입 프레임 7개와 시작점, 전이를 등록했다. 팀 라이브러리 게시는 수행하지 않았다. 앱 코드 변경, Android와 iOS의 빌드, 자동 테스트, 기기 실행과 실제 프로토타입 재생은 수행하지 않았다. 코드 조사는 위 기준 커밋의 공통 코드이며 플랫폼별 제스처 연결의 실제 동작은 구현 단계에서 확인해야 한다.

# 새로고침과 목록 끝 상태 설계

2026-10-16 작성. 목적은 홈, 피드, 발견, 내 서재의 당겨서 새로고침과 하단 피드백을 Figma 상태와 구현 단위로 연결하는 것이다. 설계와 구현, 검증 결과를 구분해 기록한다. Figma 시안이나 빌드 성공만으로 기기 검증 완료를 뜻하지 않는다.

## 확정 범위

- 맨 위에서 아래로 당겨 현재 화면의 데이터를 다시 조회한다. 기존 내용과 검색 입력, 제출 검색어, 정렬, 필터는 요청 중과 실패 후에도 유지한다.
- 콘텐츠가 없거나 화면보다 짧아도 위쪽 당김이 가능하다.
- 맨 아래에서는 콘텐츠가 살짝 당겨졌다 돌아오며 기존 추가 조회의 대기, 로딩과 실패 시 재시도를 표시한다. 다음 페이지가 없으면 끝 안내와 전용 영역을 렌더하지 않는다. 헤더, 탭 바, 홈의 읽는 중 바는 고정한다.
- 사용자가 기존 페이지네이션 유지를 선택했다. 새 페이지네이션은 추가하지 않는다.
- 내 서재 편집 모드에서는 당겨서 새로고침을 비활성화한다. 편집을 끝내면 다시 사용할 수 있다.

### 상단 인디케이터

메인 컴포넌트 세트 [책췍/PullRefresh](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=1184-428)는 디자인 시스템 섹션 `1201:826`의 메인 컴포넌트 영역 `1196:1623`에 등록되어 있다.

| 상태 | 표현 | 동작 |
| --- | --- | --- |
| Idle | 숨김 | 당김 전 상태 |
| Pulling | 당겨서 새로고침, 화살표 없음 | 거리와 함께 점차 드러남. 임계점 전에 놓으면 요청 없이 복귀 |
| Ready | 놓으면 새로고침, 화살표 없음 | 임계점 도달. 놓으면 요청 시작 |
| Pending | Refreshing과 같은 링과 문구 | 기존 프로토타입 연결용 호환 상태. 별도 지연 없음 |
| Refreshing | C 검정 컨테이너, Inline progress와 새로고침 중이에요 | 시작 즉시 표시. 최소 300ms와 요청 완료를 모두 충족한 뒤 접힘 |
| Success / Error | 공통 인디케이터 접힘 | 성공은 데이터 교체. 실패는 기존 내용 유지와 공통 오류 다이얼로그의 다시 시도 및 닫기 |

상단 표시 영역의 기본 높이는 64pt이며 확대 글자에 따라 늘어난다. 새로고침 임계점은 공식 Box 기본값 80dp다. 로딩 벡터는 기존 `Loading/Inline progress` 메인 `1058:411`의 20 x 20 인스턴스다. 첫 조회의 전체 로딩 화면과 갱신 중 상단 표시를 분리한다.

### 하단 당김과 상태

메인 컴포넌트 세트 [책췍/ListBoundary](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=1184-441)를 등록했다.

| 상태 | 표현 | 동작 |
| --- | --- | --- |
| Pending | 다음 내용을 요청하고 있어요 | 기존 추가 조회 조건이 충족되면 요청. 중복 호출 금지 |
| Loading | 기존 Inline progress와 더 불러오는 중이에요 | 500ms 이후 마지막 항목 아래에서 표시 |
| End | 숨김, 전용 영역 없음 | 다음 페이지 요청 없음. 2026-10-16 기기 피드백으로 이전 끝 문구를 폐기했다. |
| Error | 불러오지 못했어요와 다시 시도 | 기존 항목과 커서 유지. 사용자 재시도 전 자동 반복 금지 |

하단 콘텐츠 이동은 시안값 최대 24pt, 놓은 뒤 복귀는 220ms Ease out이다. 헤더와 탭 바는 움직이지 않는다. Android 기본 overscroll과 별도 효과가 겹쳐 두 번 움직이지 않게 한다. 짧은 목록과 빈 화면에서는 상단 갱신을 지원하되 존재하지 않는 다음 페이지를 요청하지 않는다.

프로토타입은 상단 Idle, Pulling, Ready, Pending, Refreshing의 5개 프레임과 하단 정지, 당김의 2개 프레임에 연결했다. 최초 상단 Pending 이후 500ms 전이는 2026-10-21 즉시 표시로 대체했다. 하단 release 후 220ms 복귀는 유지한다. 상단 완료 복귀는 클릭으로 표현하며 실제 API 응답 시간을 모사한 것은 아니다. 연속적인 손가락 저항감과 인디케이터 회전은 앱 구현 후 기기에서 확인해야 한다.

## 화면별 연결

설계 당시 코드 조사 기준은 `origin/an-develop`의 `ad6280a20886d4758274c2db61de56d8dec48a5a`다. 아래 소스 경로는 `android/shared/src/commonMain/kotlin/com/chaekchaek/app/` 기준이다.

| 화면 | 현재 조회 | 상단 갱신 | 하단 |
| --- | --- | --- | --- |
| 홈 | `HomeViewModel` -> `PopularBooksRemoteRepository.homeFeed()` | 홈 데이터 갱신. 읽는 중 바 유지 | 화면 페이지네이션이 없어 하단 안내 없음 |
| 피드 | `FeedViewModel` -> `ReviewFeedRemoteRepository.reviewFeed(page, viewer)` | 감상과 스포일러 공개 상태 유지 | `nextPage`가 있으면 기존 sentinel 자동 조회, 없으면 하단 안내 없음 |
| 발견 기본 | `SearchRoute` Idle -> `DiscoverLanding` -> 공용 `HomeViewModel` | 추천 데이터 갱신. 입력과 최근 검색어 유지 | 화면 페이지네이션이 없어 하단 안내 없음 |
| 발견 검색 | `SearchViewModel` -> `BookSearchRemoteRepository.search(query, sort, page)` | 마지막 제출 검색어와 현재 정렬로 갱신. 미제출 입력 유지 | `nextPage`가 있으면 기존 sentinel 자동 조회, 없으면 하단 안내 없음 |
| 내 서재 | `ArchiveViewModel` -> `LibraryRemoteRepository.getAll(token)` | 독서 상태 필터, 정렬, 책등 토글 유지 | repository가 모든 API 페이지를 읽으므로 화면은 하단 안내 없음 |

검색 결과 없음과 서재 필터 결과 없음도 같은 조회 조건으로 갱신한다. 비로그인 서재는 현재 토큰이 없어 조회하지 않는다. 당김을 새 로그인 흐름으로 바꾸거나 서버 재조회 성공으로 표시하지 않는다. Figma의 빈 서재 예시는 로그인 후 항목이 없거나 필터 결과가 없는 경우다.

## 구현 순서

1. **조회 상태 분리**: 첫 조회와 `refresh()`를 구분한다. 기존 Content 또는 Empty를 유지하면서 요청 진행, 인디케이터 노출, 갱신 오류를 별도로 관리한다. 현재 `retry()`의 전체 Loading/Failure 전환을 그대로 호출하지 않는다.
2. **공통 제스처와 표시**: 화면 높이 이상인 스크롤 컨테이너로 빈 화면도 당김을 받게 한다. 상단 단계, 하단 저항과 복귀, 상태 footer를 연결한다. 현재 Compose 의존성에서 지원하는 표준 API를 확인해 선택한다.
3. **화면과 요청 경계 연결**: 기존 검색과 필터, 페이지네이션, 인증 경계와 연결한다. 아래 경쟁 요청과 내 서재 쓰기 경계를 처리한다.
4. **회귀 검증**: ViewModel의 요청과 상태 테스트 후 Android와 iOS에서 같은 시나리오로 거리, 저항, 고정 바, 접근성을 확인한다. 공통 코드와 플랫폼별 연결을 함께 확인하고 결과는 플랫폼별로 보고한다. Figma 시안값은 기기 검증으로 조정할 수 있다.

### 요청과 상태 보존

- 요청 진행 여부와 표시 시간을 구별한다. 당김을 놓으면 링과 문구를 즉시 표시하고 최소 300ms 유지한다. 실제 응답은 대기 없이 화면에 반영한다. 300ms가 지나도 요청 중이면 표시를 유지한다. 표시 중에는 중복 당김 요청을 막는다. 첫 조회와 추가 페이지 로딩에는 기존 500ms 규칙을 유지한다.
- 같은 화면의 반복 당김은 요청 한 건으로 제한한다. 공용 HomeViewModel을 사용하는 홈과 발견 기본도 동일 요청을 중복 실행하지 않는다.
- 갱신 시작 시 이전 추가 조회를 취소하거나 응답을 무효화한다. 갱신 중 새 추가 조회를 막고, 성공 후 새 커서만 사용한다. 실패 시 기존 커서를 유지한다.
- 검색어, 정렬, 인증이 달라진 뒤 도착한 응답은 최신 결과를 덮지 못하게 요청 세대와 입력 snapshot을 확인한다.
- 구현안은 피드와 검색에서 이미 읽은 페이지 범위를 다시 조회한 뒤 원자적으로 교체하는 것이다. 새 데이터가 일찍 끝나면 새 끝을 따른다. 중간 페이지 실패 시 기존 목록을 유지해 새 첫 페이지와 오래된 다음 페이지가 섞이지 않게 한다. 현재 구현도 이 방식으로 동작한다.
- 검색 입력 `query`와 제출 검색어 `currentQuery`를 유지한다. refresh가 `search(query)`를 호출해 미제출 검색을 실행하거나 최근 검색어 순서를 바꾸거나 `cc_search_submit`을 다시 기록하지 않게 한다.
- 홈과 내 서재의 탭 재선택은 기존 맨 위 이동을 유지한다. 서버 목록을 SavedState에 저장하지 않고 기존 검색어, 정렬, 페이지 복원 단서를 사용한다.
- 설계 당시 서재의 조회와 쓰기는 `libraryJob`을 공유했다. 구현에서는 조회 작업과 쓰기 작업을 분리하고 같은 mutex로 직렬화했다. 갱신은 진행 중인 삭제와 독서 상태 변경을 기다리며 취소하지 않는다. 회원 진입과 로그아웃에서는 이전 세션의 조회와 쓰기를 취소하고, 동일 회원의 토큰 갱신에서는 쓰기를 유지한다. 사용자 확정 정책은 편집 모드에서 당겨서 새로고침을 비활성화하는 것이다. 편집 진입 시 진행 중인 당김을 접고, 편집을 끝낸 뒤 다시 허용한다. 삭제와 독서 상태 변경의 기존 선택 및 요청 흐름을 유지한다.
- 실패 시 기존 내용 또는 빈 상태를 보존하고 공통 오류 다이얼로그로 재시도를 안내한다. 추가 조회 실패를 데이터 끝으로 처리하지 않는다.

## 공식 Box와 단순 인디케이터 교체

2026-10-19 사용자가 A 잉크 링 대신 [기존 로딩 화면](https://www.figma.com/design/tn59Thk2GRcVLkzoO8k9Sr?node-id=1188-1258)의 20dp 주황색 로더와 안내 문구를 사용하기로 결정했다. 사용자가 승인한 공식 `PullToRefreshBox`의 기본 임계값 80dp를 유지한다. 이전 시안의 64pt는 인디케이터 표시 영역의 기본 높이이며 새로고침 임계값이 아니다. 현재 의존성인 Material 3 `1.10.0-alpha05`의 공통 소스와 [공식 API](https://kotlinlang.org/api/compose-multiplatform/material3/androidx.compose.material3.pulltorefresh/-pull-to-refresh-box.html)를 대조했다. Box에는 threshold와 enabled 인수가 없으므로 기본값을 사용하고 편집 중에는 Box의 제스처 노드를 분리한다. 라이브러리 추가나 버전 변경은 없다.

| 상태 | 현재 표현 |
| --- | --- |
| Idle | 숨김 |
| Pulling | 당겨서 새로고침, 화살표 없음 |
| Ready | 놓으면 새로고침, 화살표 없음 |
| Pending | 갱신 요청 중, 로더 없음 |

- `BookDetailViewModel.refreshState`를 감상 초기 로딩과 분리한다. 갱신 중 기존 책 정보, 감상, 범위와 정렬, 목록 위치, 화면의 saveable 입력을 유지한다. 읽던 페이지까지 재조회하고, 도서와 감상 요청이 모두 성공하면 결과와 다음 페이지를 함께 반영한다. 실패하면 기존 정보와 커서를 유지하고 공통 스낵바의 다시 시도로 복구한다.
- 중복 새로고침과 갱신 중 추가 페이지 요청을 막는다. 정렬과 범위, 인증 또는 책 변경은 이전 갱신을 무효화한다. 저장 요청은 당김으로 취소하지 않으며 쓰기 중에는 당김을 비활성화한다. 저장 성공이 갱신을 대체할 때는 기존 조회 세대를 무효화한다. 복원 페이지 번호는 유효한 응답을 반영하는 시점에만 저장한다.
- Android와 iOS는 공통 화면과 ViewModel을 호출한다. 상세 하단은 기존 페이지 로딩과 실패 재시도를 유지하며 이번 변경에서 하단 당김 효과를 추가하지 않는다.
- 객체지향 구조의 기존 한계: `BookDetailViewModel`이 추상 저장소 대신 구체 `BookDetailRemoteRepository`와 `LibraryRemoteRepository`에 의존해 DIP를 위반한다. 이번 요청은 새로고침 확장이므로 저장소 계층 전체의 분리는 포함하지 않는다.

## 최신 an-develop 통합 (2026-10-21)

병합 기준은 `origin/an-develop`의 `19c98f89`다. 질문 A의 자료 패널과 가려진 컨트롤 처리, 홈·피드의 바로 담기, 인증 갱신과 쓰기 요청의 소유권을 유지한 채 5개 화면의 당겨서 새로고침을 연결한다. 실패는 기존 내용과 커서를 보존하고 공통 오류 다이얼로그에서 동일한 작업을 재시도한다. 새로고침의 즉시 표시·최소 300ms 정책과 편집 중 서재 새로고침 비활성화는 유지한다.

서재는 최신 읽기 요청 세대와 쓰기 mutex를 유지한다. 삭제 완료가 대기 중인 새로고침을 대체하면 완료 후 조회 한 번으로 합치고 삭제 요청 자체를 취소하지 않는다. 피드·검색의 하단 실패는 자동 반복을 막으며, 하단 오류 문구와 공통 다이얼로그를 중복 표시하지 않는다.

통합 과정에서 Android 공통 테스트 379개와 앱·테스트 APK 빌드 및 lint가 통과했다. 최종 코드 재빌드, 양 플랫폼 실행 및 원격 CI 결과는 [PR #530](https://github.com/woowacourse-teams/2026-chaekchaek/pull/530)의 검증 기록을 기준으로 확인한다. 이전에 사용자가 확인한 물리 기기 APK는 `f415f5d6`이며 이 통합본의 물리 기기 검증을 대신하지 않는다.

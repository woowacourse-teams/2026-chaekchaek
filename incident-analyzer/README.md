# 책췍 장애 분석 서비스

Grafana의 원본 Slack 알림을 유지하고, 장애 정보와 분석 요청을 분리한다. Grafana Webhook을 수신해도 LLM 호출이나 추가 Slack 발송을 시작하지 않는다. Java 21, Spring Boot 4.1, 별도 H2 파일 DB를 사용하며 단일 인스턴스로 실행한다.

## 장애 접수

- `POST /internal/alerts/grafana`는 Bearer 인증, 256 KiB 본문 제한, 최대 100개 알림을 검증한다. `truncatedAlerts`는 `0`이어야 하며 영속 저장 후 `202`로 응답한다.
- `orgId + env + fingerprint + startsAt`으로 같은 장애를 구분한다. 반복 알림은 같은 기록을 갱신한다.
- 복구가 먼저 도착해도 복구 상태를 유지한다. 복구된 장애도 이후 사용자의 질문 대상으로 조회할 수 있다.
- 이전 버전의 `incident_job`에서는 장애 정보만 `incident`로 이관한다. 이전 자동 분석 작업을 다시 실행하지 않는다. 기존 테이블과 호출 한도 기록은 보존한다.

## 스레드 질문

Socket Mode로 `app_mention` 이벤트를 받는다. `SLACK_BOT_ENABLED=true`인 경우에도 등록된 개발 또는 운영 채널의 원본 알림 스레드에서 사람이 봇을 멘션해야 질문 작업을 만든다. 채널의 일반 메시지, 다른 봇의 메시지, 스레드 밖 멘션은 무시한다.

원본 메시지 하나만 조회하여 등록된 Grafana 발신자의 bot ID와 `CC-INCIDENT|환경|fingerprint|startsAt` 참조를 확인한다. 이를 저장된 장애 정보와 대조하고 발생 시점의 자료를 수집한다. 복구된 장애도 질문할 수 있다. 여러 장애가 묶인 알림에서는 질문에 대상 fingerprint를 적어야 한다.

Slack 이벤트 ID를 질문 ID로 사용하고 DB 저장 후 확인 응답한다. LLM 입력에는 질문, 현재 근거, 같은 스레드에서 이 서비스가 답한 최근 두 문답만 포함한다. 전체 채널이나 스레드 대화를 수집하지 않는다. 질문은 2,000자 이내이며 알려진 API 토큰과 Slack Webhook URL을 제거한다. 임의의 개인정보까지 자동으로 지우지는 않으므로 질문에 비밀값과 개인정보를 입력하지 않는다.

답변을 먼저 저장한 뒤 같은 `thread_ts`로 전송한다. 발송은 최대 3번 시도하며 모델을 다시 호출하지 않는다. 분석 중 재시작된 질문에는 중단 안내를 보내고 사용자의 새 질문을 기다린다. Slack에서 수신한 직후 서버가 중단되는 경우처럼 발송 성공 여부가 불명확하면 중복 답변이 생길 수 있다. 질문 접수부터 90초가 지났거나 자료가 없거나 일일 한도에 도달하면 LLM 호출 없이 안내한다.

앱에는 `app_mentions:read`, `chat:write`, `channels:history` 권한과 `app_mention` 구독이 필요하다. 앱 토큰은 `connections:write`, 봇은 허용 채널에 초대한다. 비공개 채널을 사용하는 경우 `groups:history` 권한이 별도로 필요하다. 앱과 봇 토큰, 채널 ID, 원본 알림의 bot ID는 [환경 변수 예시](../monitoring-server/.env.incident.example)를 참고한다.

## 수집과 모델 경계

기본 오류 로그는 5xx 최근 5분 최대 200건 중 10개 유형을 추린다. 오류 코드, 예외 클래스, 외부 API 이름과 응답 상태, 실패 종류, 배포 버전, 애플리케이션 스택 프레임만 남긴다. 메시지 원문, 요청 경로, 요청 ID, 사용자 ID, 헤더, 쿠키, 본문은 모델 입력과 결과에서 제외한다.

장애 발생 시점 기준 최근 5분과 직전 5분의 5xx 접근 로그 건수, 백엔드 수집 성공과 샘플 경과 시간, 호스트 가용 메모리와 샘플 경과 시간, Hikari 연결 대기를 고정 쿼리로 조회한다. 빈 결과를 정상값으로 바꾸지 않는다. 원본 `502`와 외부 API의 `upstreamStatus`를 구분하며 백엔드 구조화 로그 배포 전에는 외부 상태가 누락될 수 있다.

기본 자료가 충분하면 모델이 바로 답한다. 추가 확인이 필요하면 `collect_incident_evidence`에서 아래 조회 이름을 최대 4개 선택한다. 서버가 전체 목록을 검증한 뒤 고정 PromQL, LogQL만 실행하고, 조회 결과를 포함한 두 번째 모델 요청에서 보고를 마친다. 임의 쿼리문, 환경, 시간 범위, SQL과 셸 명령을 함수 인자로 받지 않는다.

| 조회 이름 | 발생 직전 15분에 확인하는 내용 |
| --- | --- |
| `db_pool_wait_peak` | pool별 DB 연결 대기 최댓값 |
| `http_latency_p95` | 전체 백엔드 HTTP 요청 p95, 초 단위 |
| `error_type_counts` | 오류 코드와 예외 종류별 5xx 건수 |
| `external_api_failure_counts` | 외부 API 이름, 응답 상태와 실패 종류별 5xx 건수 |
| `error_request_details` | 오류 요청의 정제된 경로, 인식한 예외 메시지 요약과 관측 시각 표본 |

환경과 평가 시각은 검증된 원본 장애 정보로 고정한다. 그룹 조회는 상위 5개 행과 허용된 레이블만 전달하며 결과가 더 있으면 잘림을 표시한다. 유효한 `0`, 빈 결과나 `NaN`인 `NO_DATA`, 실패한 `FAILED`, 시간이 부족한 `SKIPPED_DEADLINE`을 구분한다. 필드가 없는 배포나 트래픽이 없는 구간의 빈 결과를 정상으로 해석하지 않는다. 추가 조회마다 식, 시각, 상태, 근거 ID와 Grafana 재현 버튼을 답변에 남긴다. 요청 상세와 기본 오류 로그 버튼은 range query로, 나머지 추가 집계 버튼은 instant query로 열린다.

요청 상세는 발생 전 15분 오류 로그를 최신순 최대 200건 조회하고, 정제 후 대표 요청 유형 5개와 표본 내 건수, 첫 관측 시각과 마지막 관측 시각을 별도 E#로 추가한다. 기존 근거 ID는 유지한다. 같은 자리표시자로 가려진 원본 경로가 합쳐질 수 있으므로 전체 오류 건수나 원본 경로별 집계가 아니다. 일부 JSON, 필드 형식과 구간 밖 시각은 제외하고 제한을 남긴다. 응답 구조 오류나 API 실패는 `FAILED`, 정상 빈 결과나 모두 제외된 표본은 `NO_DATA`다.

경로는 `api`, `v1`, `oauth2`, `authorization`, `google`, `wp-includes`, `wlwmanifest.xml`, `xmlrpc.php` 등 코드에 명시한 정적 세그먼트만 남긴다. 나머지는 `{redacted}`로 가리고 query string, fragment, 세미콜론 뒤 값은 제거한다. 숫자, UUID, 이메일, 토큰과 임의 사용자 이름을 원문으로 보내지 않는다. 제어문자, 역슬래시나 경로 형식이 맞지 않는 표본은 제외하고 퍼센트 인코딩 세그먼트는 가린다. 긴 정제 경로는 `{truncated}`로 표시한다. 메시지는 스택 첫 예외 행에서 `NoResourceFoundException`의 알려진 형식이나 고정 기술 메시지만 인식해 재구성한다. 그 밖에는 정확히 허용한 애플리케이션 일반 문구만 fallback하고, 인식하지 못한 원문은 제외한다. 헤더, 쿠키, body, 사용자 ID와 요청 ID는 상세에도 전달하지 않는다. 정제 결과는 모델 입력, Slack과 저장 답변에만 남고 원본 로그는 저장하지 않는다.

원인 설명 질문에서 기본 집계만 있으면 상세 조회를 선택하도록 안내한다. 상태 코드와 건수는 증상, 첫 애플리케이션 프레임은 호출 경로로 다루며 원인으로 단정하지 않는다. 알려진 정적 리소스 탐색 경로는 원인 후보의 단서가 될 수 있으나 행위자, 침해 성공과 전체 영향까지 증명하지 않는다. 허용 목록 때문에 새 API 경로나 예외 메시지는 생략될 수 있다.

질문당 모델 요청은 최대 2회, 추가 관측 조회는 최대 4회이며 자동 재시도하지 않는다. 첫 요청에 75초 이상 남으면 도구를 제공하고 read timeout은 15초다. 35초 이상 75초 미만이면 도구 없이 한 번 답한다. 추가 조회 전에는 40초, 최종 모델 요청 전에는 35초가 필요하다. 조회 후 시간, 입력량이나 호출 한도가 부족하면 이미 얻은 자료와 제한 사유를 정적 답변으로 보존한다. 추가 조회 뒤 최종 모델 호출이나 응답 검증이 실패해도 기본 근거와 추가 조회 결과, Grafana 재현 버튼을 정적 답변으로 보존하고 분석 실패 코드와 지표를 남긴다. 첫 모델 호출 실패는 기존 오류 안내로 처리한다. HTTP connect/read 제한은 전체 처리 시간의 엄격한 상한을 보장하지 않는다.

구조화 응답과 근거 ID를 검증하며 원인 후보는 최대 3개다. 이 검증은 주장 자체의 진실성을 보장하지 않는다. 입력은 요청마다 20,000자, 출력은 요청마다 2,000토큰, 호출 예약은 한국 시간 기준 하루 20회로 제한한다. 두 단계 분석은 예약 2회를 쓰며 실패한 요청의 예약도 재시작 후 유지한다. `store=false`로 첫 요청과 응답 항목, 같은 `call_id`의 함수 결과를 전달하고, 마지막 요청은 `tool_choice=none`으로 추가 실행을 막는다. 암호화된 reasoning 항목은 연속 요청에만 사용하고 로그, DB, Slack에는 남기지 않는다.

`incident_model_request_total{phase}`는 단계별 요청 수, `incident_query_total{query,outcome}`는 고정 조회의 결과를 센다. `incident_llm_tokens_total{direction}`은 응답을 받으면 도구 인자나 보고서 검증 전에 사용량을 더하며, 저장된 답변을 재발송할 때는 더하지 않는다. HTTP 오류 등으로 사용량을 받지 못한 요청을 비용 `0`으로 해석하지 않는다.

최종 호출 실패를 복구한 답변에 저장된 토큰 수는 첫 요청에서 확인한 사용량이며 전체 비용을 뜻하지 않는다. 최종 응답을 수신한 뒤 검증에 실패했다면 그 사용량은 지표에 포함되지만 답변의 토큰 수에는 합쳐지지 않는다. 예외 원문과 검증에 실패한 모델 출력, 암호화 reasoning은 답변과 저장 기록에 넣지 않는다.

## 검증과 운영

```sh
./gradlew test
./gradlew bootJar
```

인증, 입력 계약, 중복과 순서 역전, 복구 후 조회, 기존 DB 이관, H2 재시작, 빈 근거, 민감 필드 제거, 두 단계 모델 계약, 조회 범위와 재실행 방지를 확인한다. 외부 API는 모의 서버로 검증하므로 실제 모델 품질을 의미하지 않는다. 배포 후에는 새 사용자 멘션으로 조회 선택과 근거 표시를 확인한다. 과거 질문을 자동 재실행하지 않는다. Slack 추가 권한이나 DB 변경은 필요하지 않다.

[openapi.yaml](openapi.yaml)과 웹훅 통합 테스트의 `build/generated-snippets/grafana-webhook`에서 계약을 확인할 수 있다. H2 볼륨을 유지해야 장애 정보와 호출 한도가 보존된다. 원본 로그는 저장하지 않고 질문과 답변, 장애 메타데이터를 저장한다. 기록의 자동 삭제는 아직 제공하지 않는다. `/actuator/health`, `/actuator/prometheus`는 내부 네트워크에서만 사용한다.
